# 机器人链路：AI 结果消费与手势→运动控制

覆盖「端侧 AI 的手部/姿态结果 → 机器人 TCP/串口控制」这一段。下游是**执行器**，
判据和纯视觉分支不同：**看到命令发出去了不算成功，臂真的动了才算**。

本文件只收「消费侧独有」的知识；链路/传输/验收的通用判据见同 skill 的
`tcp-and-ws-link.md`、`acceptance-scripts.md`，此处只交叉引用，不重述。

## 1. 累积量 ≠ 增量（最高频的真机故障）

### 症状指纹

> **小幅输入总是"没反应"，偶尔却突然大幅动一下。**

这个组合基本可以直接锁定病因，不必先怀疑滤波、增益或曲线。

### 根因形态

上游产出一个**累积量**：

```
delta = position − reference        // reference 只在首次稳定时锁存一次，之后永不更新
```

下游把它当"这一帧走了多少"直接用 ⇒ **只要输入保持不变，同一份位移被无限重复消费**。

| 帧 | 输入 | 消费的 delta | 换算步长 | 结果 |
|---|---|---|---|---|
| 1 | 动 1cm | 0.02 | 0.39mm | **< 死区 0.5mm ⇒ 跳过**（"卡住"）|
| 2..n | **停住** | 0.02 | 0.39mm | 一直跳过 |
| m | 稍动 | 0.03 | 0.58mm | **动一步**（"突然运动"），且基准未变 ⇒ 下一帧继续重发 |

### 为什么测试抓不到

参考实现里的同名函数收的是**调用方算好的帧间增量**，所以两端
**参数名一样、语义不同**。单测喂的是自造增量序列 ⇒ 全绿。

> 教训：**跨模块的语义契约必须显式写在类型/头文件注释里**，
> 不能靠"参数名相同"默认一致。

### 三条不变式（换任何"累积量 → 增量"适配都适用）

| 情形 | 行为 | 理由 |
|---|---|---|
| **第一帧** | 只锁基准、**不发** | 无前驱可减；从 0 起算 = 把整段累积偏移当一步发（**正是要修的跳变**）|
| **被降频/丢弃的帧** | 基准**照常推进**、只是不消费 | 否则这帧运动被"攒"着，下一帧一次性补发（**同族 bug**）|
| **输入本身无效**（如参考点未锁存）| 基准**不推进** | 无效窗口的输入不能成为后续起点 |

⚠️ **第二行最容易写错**：降频/限流的 `return` **必须在差分之后**。

反例（亲手造过）：

```cpp
if (now_ms - last_send_ms_ < period_ms) return true;   // ❌ 在差分之前
// ... 下面是差分 ...
```

被丢的帧不动基准 ⇒ 运动被银行存着、下一帧补发 —— **和原 bug 一模一样**。

### 复位点清单

差分基准（`prev_delta_` / `have_prev_delta_`）必须在这些地方清掉：

- **连接建立（`open()`）**：重连后手可能完全在别处，拿旧基准会把整段位移当一步发。
- **目标离开又回来**：回来的对象是**新原点**（其 reference 也重锁了），
  保留旧基准 = 算两个无关位置的差。

## 2. 离散事件必须冻结连续通道

### 症状

操作者做"开关手势"（如握拳 = 闭合夹爪）时，执行器**同时还在平动**。
操作者意图是"做开关，不要动"。

### 根因（两层，第二层反直觉）

1. **分类器要连续 N 帧才确认手势**（例：5 帧 ≈ 625ms @8Hz）—— 确认之前系统
   根本不知道有手势；
2. 🔑 **做出手势的姿态本身不是静止的**：握拳时手指收拢 ⇒ landmark 包围盒缩小、
   中心漂移 ⇒ 上报的 `position` 在**真实移动**。

> 别假设"做了手势的手就不动"。**手势**和**静止**是两个独立维度。

### 修法：静默窗口

- 手势**上升沿**触发 → 置 `muted_until_ms_ = now + mute_ms`（默认 500ms ≈ 确认耗时 + 余量）；
- 窗口内连续运动被抑制；
- 窗口内**每帧刷新差分基准** ⇒ 等于**丢弃**窗口内位移；
- 窗口结束从当前位置继续，**不补发**。

**"丢弃" vs "缓冲"的区别是本质的**：缓冲会在窗口结束**一次性大跳**，
用户会当成一个新 bug 报回来。**离散事件之后的连续量，默认语义永远是"丢弃"。**

留一个 `0` 的逃生门（`gesture_mute_ms = 0` 即回到旧行为），并写一条测试钉住它。

## 3. 可达域 ≠ 包围盒

`caps.workspace` 这类字段常是**几何包围盒**，**不含"运动学是否解得开"**，
实测可**虚大 1.6–3.5×**，而且原点在三轴上**不居中**。

- 后果：以为还剩 60mm 行程，实际只剩 9mm ⇒ 照发满速步长、每帧被拒。
- 判据 fork：**凡"输入位移 → 执行器位移"的换算、以及"距边界多远"的判定，
  基准一律用实测 span**，不用包围盒。
- 实测方法：用绝对定位指令二分探测"这个位姿解得开吗"（点本身的性质），
  比步进法（测一条路径）更准且可二分。留一个 `reach_span = 0` → 回退包围盒的默认，
  用于未实测的设备。

  见 `acceptance-scripts.md`（6 条通则 + 假 FAIL 清单 + 环境/状态卫生）。
- **改语义后老测试变红通常不是回归**：统一改法"先喂一帧建基准、再喂位移帧"；
  帧间隔必须 ≥ `1000/rate_hz` ms（例 66ms；写 50ms 会被限流静默吞掉），
  且第一帧只锁基准、计数会比预期少 1。
