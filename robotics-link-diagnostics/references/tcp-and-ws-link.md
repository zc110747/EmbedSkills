# 跨服务 TCP Client 链路 + 关节级 WebSocket 链路

## 一、跨服务 TCP Client 链路（客户端侧）

### 1. 什么时候用

- 需求形态：**A 服务原本只走串口/本地硬件，现在要能直接驱动 B 服务（仿真或真机）**，
  且明确要求「**新增**传输方式，不是把原有链路改造掉」。
- 典型语义鸿沟：A 是**增量**（摇杆：推杆 = 持续变化），B 是**绝对量**（关节角/目标位姿）。
- 服务端侧（B 侧加新入口）的规矩见 `backend-ingress-rules.md`：新入口只当 **adapter** —— 只调服务端控制层、
  几何/限位一律从**真值配置**推导、判据用**冻结基线**而不是自证、`Close()` 先关活连接再收尾。

### 2. 四条必须先问清的事（顺序别换）

1. **B 有没有"读当前状态"的命令？** 若 B 只有写命令，增量语义就**没有基准**可用。
   最优解是给 B 加一个**只读**查询命令（复用 B 既有的状态快照函数，通常 10~30 行），
   而不是在客户端猜一个起步角。等价的坏味道：客户端里出现写死的 fallback 起步角且没有上报。
2. **两边的"方向/单位/编号"是不是同一套语义？** 见 §3，这是最容易"两边都看起来正常"的坑。
3. **A 的原链路是否真的零改动？** 用**能力声明**（capability / `caps`）把差异显式告诉前端，
   而不是在页面里写 `if (mode === 'network')`。原按钮**置灰 + title 写明原因**。
4. **谁负责限位/IK/坐标变换？** 答案永远是 B。A 只做"翻译 + 传输"，宁可让 B 拒单再回滚。

### 3. 三个致命坑（都实测踩过）

#### 3.1) 方向语义跨链路不可直接复用

若原链路的 `invert_*` 类方向配置里含**固件方向补偿**（例如固件里某些轴出厂即反相、
其余轴按"原始值超过阈值即取负步长"处理），那么把它原样搬到没有固件层的 TCP 链路上，
**两种模式的推杆方向正好相反**（同满偏输入、同 dt 下增量**符号相反**），
而且**两边都不会报错**。修法是加一次显式换算（一轴一个分支），并写成护栏测试：

```go
// 满偏推杆 + 真实 dt=1s ⇒ 增量符号必须为正（= 与原链路同向）
func TestPushDirectionMatchesSerial(t *testing.T) { ... }
```

**判据不许"看起来对"**：用符号断言，不要靠人推杆目视。

#### 3.2) 被拒命令必须本地回滚，否则症状是"完全不动且无报错"

B 因越界拒绝某轴后，若 A 的本地目标不回滚，后续每一帧都从越界值继续累加 ⇒ 每帧都被拒
⇒ **推杆完全不动，且日志里没有任何错误**。唯一可观测判据是：

> 越界被拒 **之后**，仍然能驱动该轴（角度真的离开被拒时的值）。

把它写成断言，否则这种故障只能靠人肉发现。

#### 3.3) 并发写：单一写泵 + 每路 latest-wins + 有界队列

- 所有写只发生在**一个** goroutine 里（上层只往队列放"意图"）⇒ 同一连接上 JSON 不可能交叉。
- 摇杆这类高频意图**按维度 latest-wins**（不排队连发）；离散命令走有界 FIFO，满则丢最旧。
- `Close()` 顺序：`close(done)` → 掐连接 → `wg.Wait()` → 才置"已关闭"。
  **关闭后绝不再写**；断线后**不自动重发**被中断的命令；重连用指数退避（有上限）。
- 验收要灌一坨高频帧（如 120 帧不等待），断言：之后仍能收到**新的**合法状态、
  JSON 解析失败数为 **0**、链路仍是已连接。

### 4. 两类"看起来正常"的假象（收尾验收必查）

#### 4.1) 进程活着 ≠ 服务在服务

不少 Go 服务的 Web 监听失败只 `log.Printf`（**非** `log.Fatal`）⇒ 端口被占时新实例
**不会退出**，现场于是变成"两个同名进程、页面仍是旧那个在服务"，而重建时旧二进制会被
改名成带 `~` 后缀的备份。两者都会让人误判"已重启生效"。

- 断言"服务活着"要**打端口 / 健康检查**，不要数进程、不要看窗口还在不在。
- 启动脚本若**刻意不做端口预检**（例如它坚持不复制端口真值），就要在文档里写明这个失败模式：
  先关旧实例再启动。

#### 4.2) 重启自愈：B 重启后 A 必须自己爬起来（不用写新脚本）

这是"退避重连 + 重连后重建基准"唯一值得写的验收：

> 杀掉 B（或让 B 的启动脚本按端口杀掉旧实例）→ **完全不动 A** → 重跑同一份端到端脚本。

全绿即证明重连与基准重建都成立。把这条写进验收清单，比只靠单测里的"drop 连接"更有说服力。

#### 4.3) 入口"能驱动"≠ 对端界面显示对了（最容易漏的一条）

数字孪生类前端常画**两棵树**：主臂 = **指令**，幽灵/半透明 = **实际位姿**。
它靠**帧上的 `origin` 标签**决定要不要"命令侧跟随"。第三方入口借用"本页命令"的身份，
于是对端前端把它当成"我自己发的命令"⇒ **只有幽灵动、实体主臂不动**。
详细语义与修法见 `origin-and-follow.md`。

### 5. 端到端验收脚本（零依赖 Node，`tools/*-check.mjs` 之类）

- **期望值一律从配置派生**：读 A 的 `config.yaml` + B 的模型真值（关节 role/限位、
  执行器接线顺序），把关节角按模型 home 位换算成舵机角再比较。
  改了模型或配置，期望值跟着变 —— 否则会出现"测试绿但机器不对"。
- 引用 B 的包内路径时注意**基准目录是 B 自己的仓库根**，不是 monorepo 根。
- 手写 WS/TCP 客户端时，**Node 的 `upgrade` 回调有第三个参数 `head`**
  （紧跟握手到达的首个数据包）：不把它喂进解析器会**静默丢掉**握手后立刻发出的那帧
  （实测正是第一帧能力声明）。症状是"服务端明明发了，客户端永远收不到"。
- 等待条件按**值**等（`waitState(pred)`），不要按"新消息条数增加"等 —— 摇杆停住后永远不满足。
- **分段用例必须显式建立前置条件，而不是写在注释里**：前一段若有**时间驱动**的动作
  （按真实 dt 积分的摇杆，"推 0.5s"到底走了多远逐次不同），后一段若依赖它的结束位姿
  （例如某个方向要靠底座旋转，而底座已停在行程端点）就会**偶发 FAIL** ——
  同一脚本一次绿一次红，最容易被误判成"产品回归"。修法是后一段开头重新建立已知位姿，
  **并把它变成一条断言**（如"某段前置：回到 HOME"），失败时也能自证是前置没建立。
- 用例分组建议：能力声明 / 链路已连 / 首帧状态 / HOME 复位 / 方向符号 / 回中即停 /
  六向步进 / 两端端点 / 逐位次直控 / 越界拒绝+回滚 / 并发冲刷 / 收尾复位。

## 二、关节级 WebSocket / JSON 链路

### 6. ★★ 两棵树：主臂 = "要去哪"，幽灵 = "现在在哪"

孪生前端**同时画两棵树**：

| 树 | 数据 | 语义 | 观感 |
|---|---|---|---|
| **主臂** | 指令侧关节角 | **指令/意图**"要去哪" | 不透明 |
| **幽灵** | 实际侧关节角 | **实际**"现在在哪" | 半透明 |

★ **两棵树长期分离 ≠ 设计如此，而是缺陷。** 判据不是"看得见幽灵"，而是
**"幽灵与主臂是否重合"**。重合 = 命令侧跟随生效；不重合 = 有人动了机器而页面没跟随。

★ 状态帧里必须能表达"**这批状态是谁引起的**"。缺这个概念时，UI 只能看到
"实际 ≠ 指令" ⇒ 会把它读成**异常**（"命令已静止但误差停在 N° —— 查卡死 / 失步 / 限位截断"），
于是**只要外部入口在驱动，就一直误报**。

### 7. ★ 状态回传的通路与缺口（别把"没上报"读成"跟随坏了"）

- **"上位机下发"** 通常是**完整同步**的（命令 → 设备 → 状态帧 → 全客户端广播）。
- **"设备侧自主变化"** 常常**整条是断的** —— 因为设备改完角**什么都不回吐**。
  要让自主变化被感知，最短的三条路：
  1. **设备主动上报**（协议里定义的状态报文若已就绪，通路是现成的；做**变化触发**比周期上报省带宽）；
  2. **上位机低频轮询**（还要同时扩展解析层，否则回执仍被判为"其它"）；
  3. **前端区分来源**（即 `origin` 语义）—— 缺它就会在外部驱动时**持续误报**。

★ 另注意**结构性不对称**：同一条字节在**不同链路**上可以有不同语义与回执类型。
⇒ **加跨链路断言时必须按链路写**，并**把这类不对称登记成"设计"**，否则下一个人会把它当 bug 去"修"。
（详见 `backend-ingress-rules.md` §4）

### 8. ★ 命令门控与优先级（自主上报让位于交互指令）

- 门控模型：`inflight`（在途）/ `pending`（待发槽）+ **latest-wins**（尾沿补发）。
- ★ **"让位 ≠ 丢弃"**：被让位的动作保留**脏标志**，**在真正发送那一刻才取值** ⇒ latest-wins。
- ★ **异步事件行（带特殊前缀的推送）不参与"每条指令恰好回一行"的应答契约** ⇒
  拿它上报状态**不会**放行某条在途命令的门控。**这是它能安全插进链路的根本原因。**
- ★ **闸门用单测证、可观测后果用脚本证**：竞态/优先级类机制的窗口常常窄到脚本摸不着
  ⇒ 单测**直接构造在途态**；脚本只证"命令优先 + 被让位的动作没丢"。
- ★ **同一条字节的身份取决于"谁发出的"**：某条指令在真机链路上只可能由上位机**翻译**产生
  ⇒ 属**命令路径**；在仿真链路上只会由调试/验收脚本发出 ⇒ 应按**外部改动**对待。

## 三、不用装 Chromium 的浏览器取证（Windows）

`npx` 在沙箱里可能撞 wsl 拦截；直接用本机 Edge：

```bash
msedge.exe --headless=new --disable-gpu --user-data-dir=<tmp> \
  --window-size=1500,1050 --virtual-time-budget=7000 \
  --screenshot=<png> http://127.0.0.1:<port>
# 取 DOM：同参数 + --dump-dom（重定向到临时文件，再用 Grep 工具查，别用本机 grep）
```

用于验证**只有浏览器才知道**的事：按钮是否带 `disabled` 与原因 title、
面板可见性、实时数值是否真的写进了 DOM。

⚠️ **抓日志要认清通道**：来源提示常走页面自己的日志 store（落到页面上的日志面板），
**console 里一个字都没有**。用 CDP 的 `Runtime.consoleAPICalled` 去抓会两个关键词全 false
—— 看起来像"文案写错了"，其实只是抓错了通道。
