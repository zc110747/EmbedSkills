# 摄像头视频链路与端侧 AI 分支

## 何时用

三条链路之一需要落地或排障时：设备侧 **RTSP 推流端**（Publisher）、**流媒体服务端**（把画面低延迟送到浏览器）、**端侧 AI 旁路**（在既有管线上叠加检测/跟踪）。

先划边界：推流端只做采集/编码/推送；服务端只管子进程生命周期、信令中转与 HTTP 代理，**不解码不转码**；AI 分支必须允许整条失败而不影响视频。

## 核心知识点

| 主题 | 规则 |
|---|---|
| 可插拔后端 | 采集/管线/发布均为抽象基类 + 工厂，编译期开关取值 `auto/gstreamer/sim`；`sim` 支撑无硬件 CI，换真机只换采集实现，编码/推送/接口不变 |
| 断线退避 | 退避 1/2/5/10s，耗尽后封顶不无限增长；仅当 STREAMING **稳定保持 ≥3s** 才重置退避——异步建连会造出"假 STREAMING"，把正在升级的退避清零 |
| 配置 | 优先级 CLI > 配置文件 > 内置默认；子集解析可自写，无需引第三方库 |
| 服务端拓扑 | 推流端 --RTSP--> MediaMTX --WebRTC/HLS--> 浏览器；服务端不碰媒体本身，只做 WHEP 信令代理与 HLS 反向代理 |
| 配置真值源 | MediaMTX 运行时读的是服务端**动态生成**的配置，签入的静态配置在运行时完全不生效；改运行时行为必须改生成逻辑 |
| 单端口对外 | WHEP 与 HLS 均经服务端代理，浏览器只访问一个 HTTP 端口：端口不外露、无 CORS、手机只开一个防火墙口；HLS 代理需透传会话查询参数（LL-HLS 亲和） |
| WebRTC vs HLS | WebRTC 亚秒，但怕 UDP 被挡、怕非 https 源；HLS 数秒，纯 TCP 最稳且**定位为兜底**，故绝不能给它选最脆的变体 |
| AI 旁路保证 | `tee` 分帧 + leaky queue + `drop=true` 的 appsink：AI 慢就丢帧、绝不反压视频；推理走独立线程，编码前零阻塞 |
| 语义自洽 | `frame_id` 取视频帧计数器、`timestamp` 取 PTS；用结果序号或挂钟时间会与视频时间基准脱钩 |
| 零依赖可行 | 无 OpenCV/Eigen 时 letterbox/NMS/卡尔曼/匹配均可手写（数百行级）；5fps 采样够用，CPU 推理上限约 10fps |
| 可选依赖 | 未装推理运行时也要零警告编译、视频照跑（空实现兜底） |
| 叠加层拓扑 | 按**点数**选连接表，未知点数返回 `null` 不画 —— 硬编码 `length === N` 会让新模型静默变成"有框没骨架" |
| 前端产物嵌入 | 前端产物在**编译期**打进二进制时，只跑前端构建不影响运行中的服务；判据是用产物里带哈希的唯一文件名去二进制里搜 |
| 多轴来源 | 多个"逻辑轴"由**同一个检测框**导出时（中心横 / 中心纵 / `√(宽×高)`）天生不独立：实测两轴相关可达 **0.84**、有效自由度只有 **2**。符号配置（`invert_*`）与深度来源都修不了，只能改**相机朝向** |

## 判据与反模式

- **AI 隔离判据**：关 AI / 开 AI 两次运行，帧数与码率必须一致；且关 AI 时管线描述字符串与未加 AI 时**逐字节相同**。
- **新模式判据**：新 AI 模式必须先在**服务端白名单**放行，否则上报端的模式轮询器会在 ~1s 内把它切回去（症状是"日志打印了新模式又立刻变回旧模式"，极易误判成上报端的 bug）。详见 `references/recorder-and-mode-gating.md` §1。
- **叠加层判据**：同源数据（专用块 vs 通用对象数组）**只能画一次**，并写断言把同源关系钉住；协议里标了"消费者不得使用"的字段（如参考点未锁定时的 delta）在 UI 上必须同样不可用。
- **累积量 ≠ 增量判据**：上游报的 `delta` 若是 `position − reference`（reference 只锁存一次、
  **永不更新**），它就是**累积量**；下游要**帧间增量**时必须自己差分 `inc = now − prev`。
  症状指纹：**小幅输入总是无反应、偶尔突然大幅动一下**（每帧重发的同一份位移落在死区之下被吞，
  某帧越过阈值就动一步）。三条不变式：① **第一帧只锁基准不发**（从 0 起算 = 整段累积偏移当一步发）；
  ② **被降频/丢弃的帧仍推进基准** —— 所以**限流/降频的 `return` 必须在差分之后**，
  否则这帧运动被"银行存着"、下一帧一次性补发（自己造出同族 bug）；
  ③ **输入本身无效时不推进基准**。**离散事件（如"握拳=开关"手势）必须冻结连续通道，
  且窗口内丢弃位移而非缓冲** —— 缓冲会在窗口结束一次性大跳，被当成新 bug 报回来。
  另一层反直觉：**做出手势的姿态本身不是静止的**（握拳时 landmark 包围盒缩小、中心漂移），
  别假设"做了手势手就不动"。机器人控制侧的完整判定（三条不变式、复位点、静默窗口、
  可达域≠包围盒）见 `robotics-link-diagnostics/references/robot-control-consumption.md`。
- **前端验收判据**：构建全绿 ≠ 运行时正确。判据是"产物里有没有 `undefined`/`NaN`"**加上有区分度的正样本**（别选 `UNKNOWN` 这类"字段没绑定也正好显示"的值）；交付时列出未覆盖的层（实际像素 / 长连接 / 轮询）。详见 `references/browser-overlay-and-client-verification.md`。
- **多轴独立性判据**：从**一个**检测框算出多个逻辑轴时（中心横、中心纵、`√(宽×高)`），
  4 自由度压成 3 个输出 ⇒ 天生不独立。做多轴交互前先在**同一帧集**上测相关矩阵 + PCA：
  两轴 `|corr| ≥ 0.6`、或 PC1+PC2 ≥ 90%（有效自由度 2），就说明该轴不能当独立维用。
  **相关系数只能同对比** —— 拿 `corr(A,B)` 去比 `corr(候选, C)` 得出的"换方案更好"是垃圾结论。
  详见 `references/coordinate-mapping-and-axis-coupling.md`。
- **录制器判据**：录制目的是"可离线重放"时，服务端必须存**上报端原字节**；证据是库里仍保留上报端的定点格式（`0.0000`），而通用编码器会写成 `0`。
- 现象 → 根因：
  - 检测框乱飘 → 取 RGB 时整块 memcpy，未按 stride 逐行
  - 置信度普遍偏低 → 对已 sigmoid 的输出又做了一次 sigmoid
  - 跟踪框越收越窄直至消失 → 用固定宽高比的低维卡尔曼，宽度被外推到 0
  - 低帧率源 ID 频繁跳变 → `max_time_lost` 按 30fps 硬算，未用真实 AI 帧率
  - 改了源码行为没变 → 未重新构建，跑的是旧二进制
  - "找不到二进制" → 只探测显式路径，缺工作区内置副本与 PATH 回退
  - 重连恢复被判失败 → 读了被缓冲的 stdout 日志；判据应取实时刷盘的服务端日志
- 日志可信度：服务端日志（实时刷盘）> 推流端日志（stdout 有缓冲）> 脚本控制台（常被环境吞）。

## 采集端取证（"检测不到"先查画面，别先怪模型或人）

按这个顺序查，前一步不过就别做下一步：

1. **枚举 ≠ 可用。** `--list` 可能把**同一台物理设备列两次**（多接口/驱动重复枚举），
   按第二个索引起流会 `Failed to start` / `camera busy`。
   判据是**能否实际上流**，不是列表里有没有。更权威的设备真身来自系统枚举器（如 DirectShow 的 `VID_/PID_`）。
2. **量化画面，而不是"看起来暗不暗"。** 遮挡/失焦的可靠特征是**没有锐利边缘**：
   取 `edgedetect` 之后的平均亮度当锐度代理，与一张确证可用的参考图对比。
   实测一次遮挡：边缘能量 **0.769 vs 参考 4.287（0.18×）**，而平均亮度只掉到 0.73× ——
   **只看亮度会误判为"只是有点暗"**。三个后端/路径都拿到同样画面才能排除"曝光没收敛"。
3. **取证不要重新打开设备。** 从**正在跑的 RTSP 流**拉一帧
   （`ffmpeg -rtsp_transport tcp -i rtsp://h:p/path -frames:v 1 x.png`）：
   ①零设备争用（真机常只有一个物理设备，另开一次采集会把 agent 顶掉）；
   ②拿到的正是 tee 分支上游、**AI 分支同一路**的画面，验证力强于另开一次采集。
4. **阈值标定先看 metadata 够不够。** 若上报里已有可反算的中间量（例：21 个关键点的
   像素坐标、2 位小数），就**离线反算**，不要为了标定去改代码或重编 ——
   精度通常远高于要标定的量。**复刻公式要逐字照抄实现**（下标表、是否含 z、跳过条件）。
5. **把真值冻结成回归测试，而不是提交现场截图。** 现场帧常含操作者面部/环境，
   提交进仓库是隐私问题；而坐标向量足以钉住阈值，
   测试里逐位冻结真实向量比图片夹具更小、更精确、更无隐私风险。
6. **离线标定脚本要放进仓库**（不是临时目录）。它编码了"实现公式 + 为什么这么取阈值"，
   是后来者复核阈值的唯一入口；留在 gitignore 的 scratch 目录里等于丢失，
   文档里的引用也会变成悬空指针。

**反模式**：① 0 检出就归因"被测对象没配合"；② 只用平均亮度判断画面可用性；
③ 拿被**过渡帧**（目标入/出画面、运动模糊）污染的统计量定阈值 —— 过渡帧在分布上
天然落在两簇之间的谷底且数量占优，会把阈值**往上拉**（实测 Otsu 因此给出越界值）；
**标定时必须要求被测对象保持不动**，并用分位数/簇间距而不是全局均值。
