# 重复真值（duplicated truth）的取证与修复

## 一、什么时候该怀疑这个 bug 类

**核心特征：没有异常、没有崩溃、数值只差一点点，但"判定结果"与用户直觉相反。**

典型用户原话：

- 「本身可运行的范围，我把 X 改小，反而越界了」
- 「明明是范围内，却被判超范围」
- 「同一个输入，界面上显示能到，实际又说到不了」
- 「改了参数后本该放宽的收紧了」

**为什么特别难缠：**

1. **不报错** —— 两处都是"合法计算"，只是口径不同
2. **偏差轻微** —— 几十毫米在工作空间里不显眼，容易被当成浮点误差
3. **判定可能"碰巧对"** —— 错误的原因 + 正确的结论 = 最难发现
4. **来源随机** —— 哪一层先拒绝取决于具体数值，日志指向会跳来跳去
5. **有单侧偏好** —— 错误的量往往系统性偏大或偏小，某一片区域被整体误报

**高危场景（出现即排查）：**

- 为了让某层"少 import 一个符号"而**自己重算**一个已有函数已算过的量
- UI 层做**前置检查**（为了更好的错误信息），引擎层做**真正判定**，两者各算一遍
- 测试 helper 里为了不"污染"生产代码而复制一份算法
- 单位 / 坐标系换算在前后端各写一次
- 注释声称的公式与代码实际读的字段不一致

## 二、诊断流程（按顺序做，不要跳）

### STEP 1 — 让两个实现**同时打印**同一个输入的结果

不要读代码推演，直接在**运行时把两侧的值都打出来**。最有效的手法：
**故意把参数设成一个必然触发的极端值，从用户可见的错误消息里把内部量抠出来。**

```ts
// 探针：强制前置检查触发，从消息里抠出它算的值
store().setTargetGuard({ reachMaxOverridden: true, reachMaxMm: FLOOR });
store().moveTo(pt);
const m = /距离 ([\d.]+)mm/.exec(store().ikStatus?.message ?? '');
console.log('store 侧 =', Number(m![1]));
console.log('独立复算 =', independentRecompute(pt));
```

★ **关键**：若只有一侧能打印，就**制造**另一侧——把值塞进一个会被回显的位置
（错误消息、日志、临时插桩）。**永远不要靠读代码比对。**

### STEP 2 — 确认"差多少"，以及是系统性偏差还是随机误差

- 差 `1e-13` 量级 ⇒ 浮点误差，正常
- 差 `1e-4` 量级 ⇒ 公式相近但常数不同，通常可接受（但要知道差在哪）
- **差"一个物理量"的量级 ⇒ 就是本 bug 类**

再取**多个采样点**判断偏差形态：

| 偏差形态 | 含义 |
|---|---|
| 常数 | 少加/多加了一个常量项（偏移、零位） |
| 随某坐标线性变化 | 用错了参考系 / 轴 |
| 在某区域内为 0、区域外突然出现 | 两实现在**分支**上就不同 |
| 系统性偏大或偏小 | 用错了长度 / 半径字段（**最常见**） |

### STEP 3 — 定位哪一侧错了（**不要假设"新的那个"是错的**）

判定标准只有一条：**谁是"引擎真正执行的"那一份**。

- 找"最后真正决定结果"的实现——它通常在**被复用最多、验证最严**的地方
- 看有没有**自校验机制**：用多个姿态交叉验证同一个常量的实现，才是真值
- 交叉验证：把两侧分别与一个**第三方独立实现**（另一语言的参考实现、真机数据）比对

### STEP 4 — 找出"错的字段"是哪个（最常见根因）

**「用错了字段」是头号原因**，尤其在树 / 链表结构里。

```ts
const wrist = model.joints.find((j) => j.id === model.tcp.joint);
const radial = linkLengthOf(model, wrist.parentLink);   // ❌ 语义取反
```

排查清单：

- [ ] 层级结构里取的是 `parentLink` 还是 `childLink`？语义是不是反了？
- [ ] 取的是"**这个关节自己**的长度"还是"**它父连杆**的长度"？
- [ ] 有多个同名 / 近名字段时，取的是哪个？
- [ ] 单位是否一致（mm vs m、度 vs 弧度）？
- [ ] **注释描述的量 == 代码实际读的字段？** ← 不一致就是它

### STEP 5 — 检查"同一个坑在别处是否还有"

**必做**：用 grep 找所有"重算同一个量"的地方。一次修复往往发现两处以上。

```bash
grep -rn "parentLink\|chainLengthTo\|linkLengthOf" src/
```

★ 若这个坑**之前在测试 helper 里已经踩过并修过**，说明生产代码极可能还有同款 ——
**在测试里发现的口径坑，必须立刻回头 grep 生产代码。**

## 三、修法：转发，而不是"再算一遍（但这次算对）"

反面做法：找到错的字段、改成对的字段 —— **只修了这一处**，下次重构又会分叉。

正确做法：**让第二处消失，改为转发第一处。**

```ts
// ❌ 自己重算（即使这次算对了，也是第二个真值）
function wristDistance(model, target) {
  const pivotZ = chainLengthTo(model, shoulder.id);
  const radial = linkLengthOf(model, wrist.parentLink);   // 易错
  return Math.hypot(r - radial, target[2] - pivotZ);
}

// ✅ 转发：与引擎同一份真值
function wristDistance(model, target) {
  const geometry = ikGeometry(model);
  const { dr, dz } = wristSagittal(geometry, target);
  return Math.hypot(dr, dz);
}
```

**"为了少 import 一个符号"是错误的经济学。**
多一条 import 是可测量、可登记、可测试的代价；
多一份真值是**不可见、不可测、会腐烂**的代价。

⚠️ 转发后要处理**返回类型变化**（原实现可能返回 `null` 表示"算不出"，
真值函数通常直接抛错或恒有返回值）—— 调用点要跟着改。

## 四、防复发：三层硬化

### 第 1 层 — 架构层：登记跨层依赖

若有"层级边界白名单"，**把新的跨层 import 登记进去并写清理由**。白名单要**双向断言**：

- 正向：出现白名单外的符号 ⇒ 失败
- 反向：白名单里列了但实际没 import ⇒ 也失败（防白名单腐烂）

这样"扩边"是**显式的、被记录的**决定，而不是悄悄发生。

### 第 2 层 — 测试层：把"两侧相等"写成断言（最关键）

不要只测"结果对"，要测**"两侧口径一致"**：

```ts
it('★★ 前置检查的量必须与引擎同口径', () => {
  store().setTargetGuard({ reachMaxOverridden: true, reachMaxMm: FLOOR });  // 强制触发
  let checked = 0;
  for (const a of [0, 0.25, 0.5, 0.75, 1]) {
    for (const b of [0, 0.5, 1]) {
      const pt = samplePoint(a, b);
      store().moveTo(pt);
      const m = /距离 ([\d.]+)mm/.exec(store().ikStatus?.message ?? '');
      expect(m, `前置检查未触发，无法核对`).not.toBeNull();
      expect(
        Math.abs(Number(m![1]) - independentRecompute(pt)),
        `口径不一致 @ ${a}/${b}`,
      ).toBeLessThan(1e-3);
      checked += 1;
    }
  }
  expect(checked).toBe(15);   // 防"空集通过"
});
```

⚠️ **必须扫多个采样点**（偏差可能是位置相关的），且**必须断言采样计数**，
否则循环条件写错会"空集通过"。

### 第 3 层 — 文档层：把"为什么转发"写在代码里

转发点上方写清**事故经过**（哪两个值、差多少、症状是什么）。
后人看到"为什么不直接算一下呢"时会读到这段，从而不再重复。

## 五、诊断话术（给用户的解释结构）

这类 bug 的解释要**先破掉用户的前提**，再给根因：

1. **先纠正前提**："这不是'本来能跑、改小了就不能跑'"——那个点本来就失败，只是原因不同。
2. **给出两个数**，让差距自己说话。
3. **解释症状成因**：错误的量系统性偏小 ⇒ 内圈一片实际不可达被误报为可达 ⇒
   用户看到的"可运行范围"是**虚的**。
4. **点明"报错碰巧对"**：结论对、依据错，所以最难发现。
5. **给修法与防复发**：转发 + 登记 + 双侧断言。

⚠️ 不要只修不解释 —— 用户需要知道"我之前看到的现象里有多少是不可信的"。
