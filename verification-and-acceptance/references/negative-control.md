# 负向对照：证明**验收脚本**有牙齿

配套 [`host-load-playbook.md`](./host-load-playbook.md) §3。

---

## 一、问题

一个"永远 PASS"的脚本比**没有**脚本更危险：它给出的是**虚假的信心**。
判断一个验收脚本有没有牙齿，唯一有效的方法是让它去测一个**已知坏的**被测对象。

---

## 二、做法：用编译开关把旧缺陷**重新打开**

优先选"存在一个宏/开关能让旧行为复现"的缺陷。本项目正好有：

```cpp
/* net_socket.hpp */
#if defined(_WIN32)
#ifndef FD_SETSIZE            // ← 这个 #ifndef 让命令行 -D 能覆盖
#define FD_SETSIZE 8192       // 修复后的值
#endif
#include <winsock2.h>
#endif
```

于是**同一份源码**、不碰生产代码，就能编出"旧行为"的服务器：

```bash
# 用同一份源码编一份"旧行为"的服务（把曾经的缺陷重新打开）
g++ -std=c++20 -O2 -Iinclude -Iapp -DFD_SETSIZE=64 \
    app/chat_server.cpp app/net_socket.cpp app/yaml_config.cpp \
    -o /tmp/legacy/chat_server_legacy.exe \
    -lws2_32 -static-libgcc -static-libstdc++ -static -pthread

# 用【同一个】验收脚本去打它
python app/tools/verify_chat_load.py \
       --server /tmp/legacy/chat_server_legacy.exe \
       --only-scale --clients 100 --senders 8
```

> `--only-scale` 与 `--senders` 这类开关要**一开始就设计进去**：负向对照往往只想跑一小部分场景，
> 全量跑浪费时间且输出冗长。

## 三、期望结果：**失败**，且签名与手工复现**一致**

实测输出（节选）：

```
FAIL  watch ceiling is 8191                     (got 63)
FAIL  a 1000-connection burst loses none        (refused 37)
FAIL  packets_out == senders*(clients-1)        (got 372, expected 792)
...
LOAD relay: FAIL (11/18 failed)
```

**为什么这组数字才叫"有牙齿"**：

| 签名 | 与手工复现的对应 |
|---|---|
| `ceiling 63` | 63 客户端 + 1 监听 = `FD_SETSIZE` 64 —— 与探针测出的容量一致 |
| `refused 37` | 与"突发连接被内核拒"同一现象 |
| `packets_out=372 ≠ 792` | 说明**转发真的少了**，而不是断言写错了 |

三个数字**互相独立**地指向同一个缺陷 ⇒ 脚本测的就是那个缺陷，不是别的东西。

## 四、什么时候跑它

| 时机 | 跑吗 |
|---|---|
| 交付一个**新的**验收脚本时 | ✅ 必须跑一次，并把数字记进交付说明 |
| 每次 CI | ❌ 通常不跑（要求能编出坏二进制，且它**总是失败**） |
| 脚本改动后（改了判据/断言） | ✅ 建议重跑，确认"有牙齿"这件事没退化 |

把编译命令固化进脚本的一个 `--legacy` 开关（或写成注释/README 片段），
下次复核就是一条命令的事，而不是重新考古。

## 五、"脚本恒绿"的其它免疫手段

负向对照是**最强**的一条，但不总是可行（可能没有能复现旧行为的开关）。补充手段：

### 5.1 让断言**必然**覆盖边界值

- 发送者必须包含**最后一个接入**的客户端（历史上隐身的那一类）；
- 断言必须包含**聚合恒等式**（`packets_out == senders × (N−1)`），
  而不是"至少收到了 N 个包"这类弱条件；
- 每个"应该为 0"的计数（拒绝数、丢包数、溢出数、泄漏数）都要显式断言 == 0。
  **"没检查" 和 "检查了为 0" 是两个完全不同的状态。**

### 5.2 打印 P/F 计数

```
LOAD relay: PASS (104 checks)
```

写死期望的总数（或在 CI 里比对），这样**少跑了几条检查**也会被发现。
"PASS" 而不打印数字，就失去了这个信号。

### 5.3 故意制造失败（变异测试的最小形式）

临时把被测服务的某个阈值改坏（例如把 `out_buffer_bytes` 改成 1），
确认**对应的那一条**断言失败、而其它断言依旧通过。
如果改坏了却只有"无关的几条"失败，说明断言挂错了位置。

### 5.4 断言要"可失败"地写

- ✗ `check(len(packets) >= 1, ...)` —— N−1 个对端里只查总数，很容易恒真；
- ✅ `check(all(...), ...)` 或逐项 `check_eq`。
- ✗ `check(tag in received())` —— TCP 合并后可恒真；
- ✅ `check(hit_once(tag) == 1)` —— 只有真正整包到达才为真。

### 5.5 别用"等待"掩盖失败

- ✗ `time.sleep(2)` 之后再断言 —— 慢机器上必 flaky，快机器上可能掩盖竞态；
- ✗ 断言失败就 `return`/`continue` 掉整段 —— 后面的检查就全不跑了；
- ✅ 先 `wait_until(前置条件)`，再**无条件**断言；失败记录后继续跑。

## 六、检查清单

- [ ] 存在一份"能复现旧缺陷"的构建方式（宏开关 / 旧分支 / 桩）。
- [ ] 用它跑**同一个**验收脚本，确认**失败**且签名可解释。
- [ ] 失败签名里的关键数字与**手工复现**得到的一致。
- [ ] 负向对照不常驻 CI，但编译命令被固化下来（脚本开关 / README 片段）。
- [ ] 脚本打印 P/F 计数；CI 里比对期望总数。
- [ ] 每个"应为 0"的计数都有显式断言。
- [ ] 边界值（第一个 / 最后一个 / 容量边界 ±1）都被覆盖。
