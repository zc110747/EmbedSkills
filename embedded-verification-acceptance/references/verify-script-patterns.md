# 验证脚本模式与判据

## 一、核心原则

**脚本给出 pass/fail 计数与退出码**，而不是人肉看日志。任何"看日志觉得没问题"的结论都不算验收。

### 1.1 通用计数骨架（串口 / 网络 / 文件产物都适用）

```python
import sys
checks = 0; passed = 0
def chk(name, cond):
    global checks, passed
    checks += 1; passed += 1 if cond else 0
    print(f"[{'PASS' if cond else 'FAIL'}] {name}")
# ... 各项检查 ...
print(f"\n** {passed}/{checks} checks passed **")
sys.exit(0 if passed == checks else 1)
```

- 端口 / 设备等外部输入**从命令行取**（`--port`），不要把本机分配值写死。
- 支持 `--in <文件>` 离线复跑：把一次真实抓取存下来，之后不接硬件也能回归。
- 串口捕获前先 `reset run`，否则错过启动 banner。

### 1.2 已实测有效的几种形态

| 形态 | 做法 | 适用 |
|---|---|---|
| 串口自测 | pyserial 发命令、收响应、逐条 `chk()` 断言（菜单导航 / 按键 / 错误处理等分组） | 有 UART 命令接口的固件 |
| 协议批量验证 | 构造请求报文、解析响应，对每项错误计数（如 `n/n PASS` 或失败项明细） | 网络 / 工业协议 Agent（SNMP 等） |
| **离线逻辑单测** | 纯逻辑（编解码 / 校验 / 报文构造）在 PC 用 gcc 编译成 `.so`/`.dll`，python `ctypes` 调用断言 | 不依赖硬件，CI 友好 |
| 视觉渲染测试 | `PrintWindow` 截图 + Pillow 亮像素检测，验证每页非空白 | 桌面仪表盘 / GUI |
| 网络链路 | `ping` 全尺寸扫、`curl \| grep -q "<特征串>"`、`arp -a` 核 MAC | 以太网 / Web / 推流 |

## 二、★ 验收脚本的"前提"纪律 —— 假 FAIL 先怀疑脚本自己

脚本报 FAIL 时，**先怀疑"前提没成立"，再怀疑产品代码**。最常见的四类自造 FAIL：

1. **动作不产生可观测变化**（目标 == 当前位置 / 已贴着边界）⇒ "等收敛"拿到 `NaN` / 空集。
2. **造前提的常量写死**，没从真值（限位、容量、量程）里挑 ⇒ 撞边界后把"边界现象"误报成"机制缺陷"。
3. **一条断言证多件事** ⇒ 失败无法归因，只能猜；也别把"后来的合理变化"断言成"没收敛"。
4. **断言的机制窗口窄到脚本摸不着**（竞态 / 优先级闸门）⇒ 该由单测构造在途态来证，e2e 只证外部可观测后果。
5. **边界用例写死了数字**，没跟着真值源走 ⇒ 真值源一改，用例就静默变成"另一件事"。
   实测：`("speed 4.1", ...)` 本意是"超上限应被钳位"，量程由 4.0 改到 4.5 之后
   4.1 **反而合法**，用例照样 PASS，但已不再验证"超限钳位"这件事 ——
   属于"绿着失效"。取值方式见 §七.5。

> 与「没报错 ≠ 有数据」同源：**否定性结论一律先查"工具的观测能力"**，别把"我没观测到"直接当成"它没发生"。
> 写任何 e2e 脚本前过一遍这五条。

## 三、「没报错 ≠ 有数据」的正向验证

- 错误日志常被限流，"调用返回 0"不等于"数据正确"。
- 手段：符号取址（`arm-none-eabi-nm <elf> | grep <symbol>`）→ OpenOCD `mdw` / gdb `x/...` 直读内存里的数据结构，比对预期值。
- 例：传感器采样值、双缓冲索引交替、内存池完整性，均靠直读内存而非只看日志。
- 日志开关类特性可由此正向验证：日志宏整体关闭后，UART TX 环形缓冲的写指针必须一个字节都没动过（一次性脚本断言 `head==0 && busy==0` 应全 PASS）。约定：ISR 内不调带互斥量的日志宏。

## 四、性能类判据（先排除"伪性能"）

**方法论**：任何"设备/固件很慢"的结论，先做**双路径对照** —— 绕过外设 vs 经过外设。两者共有的开销一定在主机侧；差异部分才是外设真实开销。

### 4.1 LVGL 首帧 / 首绘卡顿

- 常见根因**不是**字库缓存 miss，而是**一个 screen 第一次被实际绘制时的一次性 CPU 开销**（样式计算 / 排版 / draw-task 构建，可达 ~200 ms，纯 CPU、零 IO）。
- **判据要先排除伪性能**：光看刷新时间变长会误判成缓存未命中。必须同时打印字形缓存的 `miss/hit/evict` 与存储侧读增量；若增量为 0 ⇒ **零 IO**，问题在 CPU，加缓存无用。
- **正解**：抑制 flush 的**离屏预热** —— 把 `flush_cb` 临时换成 dummy（吞帧 + 立即 `flush_ready`），在启动加载页背后把每页渲染一次，把首绘开销提前吃掉。
- **回归脚本**：抓串口 → 解析每次页面切换标记 → 断言首帧 `miss == 0`、零存储读、`|首帧耗时 − 预热均值| ≤ 阈值`，退出码 0/1，并支持 `--in <文件>` 离线复跑。

### 4.2 主机侧读数造成的假延迟（30 ms 级）

```python
data = ser.read(self.ser.in_waiting or 4096)   # ❌ 无数据时会请求 4096 字节
```

读语义是"尽量凑满所请求字节数，凑不满就等超时" ⇒ 每次无数据都空等一整个 timeout，把本该 0.2 ms 返回的字节拖到 ~30 ms。
**正确写法**：`ser.read(self.ser.in_waiting or 1)`。**判据**：软件回环（完全不碰外设）若也有同样的 ~30 ms，则该开销与固件无关。
另：吞吐压测的"平均延迟"受在途窗口与波特率主导，不代表固件固有延迟；真实往返延迟要看无在途窗口的 pacing 模式。

## 五、稳定性与长运行验收

- 压测前后各查一次故障状态寄存器（Cortex-M：CFSR / HFSR）= 0，无总线故障。
- 连续数十次业务请求无失败（验缓冲 / 控制块无泄漏）。
- 长运行浸泡：周期性读取某状态量，确认其 `*_valid` 恒定不冻结（体现"以日志为准"的时序类结论要以最可信的那份日志判定）。
- 外设锁死恢复、初始化顺序这类机制问题按对应外设经验处理。

## 六、双固件（Bootloader + App）端到端验证

Bootloader + App 是**两套独立构建、固定地址共存**，分三层验收：

1. **跳转验证（Golden path）**：直烧 App + 配置 → 复位 → Bootloader 挂载 → 配置 CRC / 向量 / 签名 / 版本全过 → 等待窗口；外设连接则进对应模式（符合设计），未连接则跳 App。
2. **升级验证（升级包路径）**：把升级包 + 校验清单放进可移动介质 → 复位 → Bootloader 检测包 → 擦写 App 区 → 重启 → 打印新 App 版本。再用读回手段确认版本槽 / 配置 CRC。
3. **引擎级验证**：用 GDB 直调编程函数（见 `flash-serial-and-gdb.md`），确认不再挂死、回读一致。

- 任何校验失败都**在擦写前 abort**，已运行的 App 不被破坏（防砖设计）—— 验收时重点确认"**坏包不破坏**"。
- 内存分区与防砖设计细节按工程的链接脚本核对。

## 七、SWD 内存取证的时序与宽容度纪律

### 7.1 同一次 halt 内取完所有区域

连续两次 `dump()` 是**两次独立调试会话**，中间固件**自由运行** ⇒ 两份快照属于不同时刻。

实测：状态结构读到 `TCU1 = 9011`、帧缓冲里却是 `11390`，差 2379 counts。拿这两份数据做"状态 vs 显示是否一致"的断言，得到的是**假 FAIL**（真因是采样时刻不同，不是产品错）。

修法：一次 `init/halt` 内连续 `dump_image` 多个区域。

```python
def dump_multi(cfg, items):
    """items: [(addr, size, outfile), ...] —— 同一次 halt 内全部取完"""
```

### 7.2 运行态：结构严格 + 数值宽容 + 形状校验

运行态下这些字段每帧都在变，逐像素比对必然假 FAIL（本项目 71 字节）：占空比、编码器累计值、实时示数。

**温和但有效的做法**：把这些字段列入白名单，**并为每个字段带一条形状正则** —— 值可以抖，格式必须始终成立。

```python
if st["running"]:
    pm = st["duty_permille"]
    add(1, "{:>2}.{}".format(pm // 10, pm % 10), 0, r"\d{1,3}\.\d", "row1 占空比")
    add(2, "{:>6}".format(st["enc1"]),           5, r"\s*\d{1,6}", "row2 TCU1 累计")
    add(3, _spdr_text(st), UI_SPDR_X // FONT_W, r"SPDR:\s*\d{1,2}\.\d", "row3 SPDR")
```

- **不能整段忽略**：整段跳过就再也发现不了"字段串位 / 格式写坏"。
- **停机态仍走严格逐像素**：没有理由宽容。
- 反向注入自检：把易变字段填成期望字形 ⇒ 应 PASS；硬字段破坏 ⇒ 应 FAIL。

### 7.3 异步命令的收尾必须读回确认

shell / 串口命令由主循环**异步**解析，而主循环一轮里可能含阻塞式刷屏（本项目 OLED 约 250 ms/帧）。"注入完 `stop` 就假定停了" ⇒ 主循环还没解析到，调试会话已 shutdown，**设备带着电机转到下一次验收**。

```python
def stop_and_verify(cfg, elf, tries=3):
    for i in range(1, tries + 1):
        inject(["stop"], cfg, elf, 1200)          # 等足：> 一轮主循环
        arm = _read_u8(cfg, elf, "s_armed")
        if arm == 0:
            return True
        print("[WARN] 第 %d 次 stop 后 s_armed 仍为 %s —— 再试" % (i, arm))
    print("[FAIL] %d 次 stop 后仍未停机！请手动断电。" % tries)
    return False
```

四要点：**等足（> 一轮主循环）→ 读回状态变量 → 重试 → 失败显式告警**。
这属于"比误报更严重"的一类：误报只是白跑一轮，漏报会把硬件留在危险状态。

### 7.4 复用判据，别复制判据

运行态脚本（`verify_ui_running.py`）不重写判据，而是 set `sys.argv` 后**原样调用**停机态脚本的 `main()`：

```python
sys.argv = ["verify_ui_expected.py", "--elf", elf, "--cfg", cfg]
verify_ui_expected.main()
```

两份脚本各写一套判据，改一处忘一处 ⇒ 其中一份静默失效。

### 7.5 用例取值：参数化，不写死

凡涉及**边界、换算、单位**的用例，命令文本与期望值都必须从真值源现算：

```python
def spd_text(v10):                       # x10 → 命令行文本
    return "%d.%d" % (v10 // 10, v10 % 10)

spd_hi_cmd = "speed " + spd_text(spd_max)                     # 上限处（合法）
spd_ov_cmd = "speed " + spd_text(spd_max + spd_step)          # 超上限一步 → 应被钳回
spd_un_cmd = "speed " + spd_text(max(spd_min - spd_step, 0))  # 低于下限一步 → 应被钳回
```

**"特殊点"要用代码搜索，不要挑一个"当时看着对"的值**：

```python
# 找一个真值恰为半整数的合法设定点（定点化硬证据：整数域表达不了它）
probe = None
for v in range(spd_min, spd_max - spd_step + 1):
    if (v * cnt_per) % err_sc == err_sc // 2:
        probe = v
        break
if probe is None:
    sys.exit("[FAIL] 量程内找不到半整数真值点，无法构造定点化硬证据")
```

三个要点：

- **搜索上界写 `spd_max - spd_step`**：紧随其后的"加一步"用例要能合法执行。
- **找不到必须 `sys.exit`** —— 退化成"随便取一个"，这条断言就恒真了。
- 依赖前置状态的用例（"读当前设定值"）要在注释里写明**必须紧邻**，
  中间不得插入任何改状态的用例，否则它悄悄验的是别处的值。

### 7.6 时域判据：静态比对验不出"抖不抖"，必须采时间序列

"读数一直在跳 / 稳不稳 / 有没有抖动"这类**时域行为**，`halt` 一帧逐像素比对根本
看不出来（那一帧永远"格式正确"）。要证明它，得**连续采 N 个快照**再比较。

**采样必须在一次调试会话内做多轮**：

```tcl
init
halt ; dump_image a0 ... ; resume ; sleep 250
halt ; dump_image a1 ... ; resume ; sleep 250
; ...
shutdown
```

不要"每轮起一个 openocd 会话"：单次会话（init/halt/shutdown）约 0.5 s，采样间隔被迫
抬到秒级 —— 而**"区间锁存"唯一的直接证据就是"间隔远小于窗口的相邻两点取值一字不变"**。
间隔一大，那条判据就退化成恒绿。

**两条通用判据形态**：

| 现象 | 判据 |
|---|---|
| 值是按窗口锁存的（不是每拍更新） | 相邻采样（间隔 ≪ 窗口）中"值不变"的**占比** ≥ 阈值（每拍更新的话必然每次都变） |
| 平滑 / 滤波确实生效 | 平滑量的**极差**显著小于原始量的极差（别用 `<=`，见下） |

**"退化相等"型假判据**（本项目真踩过）：平滑判据写成 `平滑极差 <= 原始极差` —— 若平滑
**完全没生效**（两个量就是同一个数），极差相等，`<=` 照样成立 ⇒ **永远绿**。对策：

- 留**相对余量**（如 `<= 0.75 ×`）；
- 基准量本身太小时（原始量几乎不动），报 `INFO`「判据不适用」而**不要给 PASS** ——
  退化的通过比 FAIL 更有害。

**结构证据优先于数值证据**：如果固件里存在"窗口累加器 / 计数器"这类**只在窗口方案下才
存在**的变量（如 `s_disp_cnt` ∈ [0, TICKS]），采样它的推进过程就是"这套机制真在跑"的
直接证据 —— 不必靠数值间接推断。

**口径校验**：平滑量的均值应与原始量的均值同阶（同一时段）。差几十倍即说明换算算式 /
量纲写错 —— 这条专门抓"平滑没错、但折算系数错"的错误。

**收尾**：本类脚本会把执行器真转起来，务必**注入 stop 并读回状态变量确认**（见 7.3）。

### 7.7 ★ 无硬件造出物理输入（按键 / 组合键 / 拨码）

验收脚本最容易被"必须要有人按按键"挡住。其实**只要输入最终落到某个 RAM 状态变量**，
就能用 SWD 直接写那个变量来造出输入，全程无人值守 —— 而且**交付固件零改动**
（不为可测性加钩子，满足"探针/测试代码必须移出交付固件"）。

**第一步：读扫描器实现，确认"写进去会不会被刷回去"。** 典型去抖实现：

```c
if (raw != k->raw_last)          { k->raw_last = raw; k->cnt = 0; }   /* 电平变：重新计数 */
else if (k->cnt < DEBOUNCE_TICKS){ k->cnt++; if (stable != raw) stable = raw; }
else                             { /* 计数饱和：什么都不做 */ }
```

⇒ **把 `stable` 拉回真实电平的唯一路径要求 `cnt < DEBOUNCE_TICKS`**。
而 `cnt` 上电后约 `DEBOUNCE_MS` 就**饱和**、之后一直走空分支
⇒ **写一次 `stable = 1` 就长期按住**，不需要按去抖周期循环回写。
（这点违反直觉：直觉会以为"必须 10 ms 刷一次"。**必须回到实现里核对**，
不同扫描器写法结论可能相反 —— 若实现是"每拍都无条件 `stable = raw`"，就只能循环刷。）

**第二步：三种语义分开造。**

| 想造的动作 | 写法 |
|---|---|
| **按住**（持续） | 只写"去抖稳定位 = 1"，**不动**去抖计数 |
| **松开** | 稳定位 = 0 **且** 去抖计数 = 0（让扫描重新走一遍去抖才回落到松开态） |
| **上升沿 / 单击** | 稳定位 = 1 **且** 边沿锁存位 = 1（真实硬件上这两位由同一次扫描一起置起） |

**第三步：前提读回确认。** 注入前断言"去抖计数已饱和"（或等价前提），
不成立就**显式 FAIL 退出**。否则"写进去被刷回去"会被读成"固件没响应"，
白排查一整轮 —— 而且更糟的是可能反过来让判据"通过"。

**第四步：★ 给注入加"目标侧见证" —— 上一步说的"长期生效"是真会被外力抹掉的。**

上面那句"**把 `stable` 拉回真实电平的唯一路径要求 `cnt < DEBOUNCE_TICKS`**"
**是全部风险所在**：`cnt` 一旦被清零，注入的按住态就没了。而清零它**不需要你动手**：

| 事件 | 扫描器里发生什么 | 注入的按住态 |
|---|---|---|
| 无人碰按键 | `raw == raw_last` 恒成立，`cnt` 一直饱和，走空分支 | **长期保持** ✅ |
| **手指碰一下按键 / 接触抖动 / 排线松动** | `raw != raw_last` ⇒ `raw_last = raw`、`cnt = 0`；<br>`cnt` 再次爬到阈值时 `stable != raw` ⇒ **`stable` 被改回引脚真实电平** | **当场作废**，且**固件侧不留任何痕迹** ❌ |

⚠️ **这不是固件缺陷，别去改固件**：真人按键时电平变一次就稳定了，扫描随后把 `stable`
收敛到"按下"，手势照常累积；被抹掉的只是"脚本伪造、而引脚并不承认"的那个按下态。
**但它的症状是"整条用例零变化"** —— 报告会写成"分支/分流没生效"之类**指向固件**的结论，
是本类假 FAIL 里最贵的一种（本项目实测：全套跑时某回归用例红、单独跑该套件却全绿，
正是开发中手指碰到了板子）。

对策 —— 用**目标自己**的量做见证：

1. **找见证量**：固件里往往已经有"已按住时长"这类计数器（每拍 `+= 扫描周期`、
   松手归零），或者任何"只在按住期间推进"的量。没有的话，可以用两个状态量的
   **组合**（例如"按住标志 + 计时/计数"）间接判。
2. **在同一个会话内、松开之前读它**。⚠️ 松开那一步会写"稳定位 = 0"，下一拍就把
   计时清零 —— 会话外再读只会拿到 0，分不清"没按住"和"已松开"。
   （`halt` 期间目标时基暂停，所以这次读取不会偷走按住时长。）
3. **判据**：被抹掉时该量会**从 0 重新累加**，与期望时长**差一个数量级**；正常时
   ≈ 期望值。实测容差：主循环是 10 ms 自校正门控时，误差 ≤ 1 拍（100 ms 容差足够），
   "被抹掉"一侧是 **0** ⇒ 两档相差一个数量级，判据不会被容差泡软。
4. **不达标时**：`[WARN]` + **重测一次**；连续两次不达标 ⇒ 以"**测试前提不成立、
   本条不是固件缺陷**"退出，**不要产出判据**（同"拒绝在错误前提下判 PASS"的纪律）。
   一次自动重测是值得的：单次触碰是瞬态的，重测能救回整轮；
   两次都坏说明环境真的在动，此时唯一正确的动作是停下来提示操作者松手。

**第五步：开跑前加"静止门"。** 读「原始电平 / 稳定态 / 已按住时长」三者，
**任一非零**即拒绝开跑，并打印"请松开按键、不要触碰板卡后重新运行"。

> ⚠️ ⚠️ **"去抖计数已饱和"不能用来判"此刻没人按键"** —— 计数只证明"曾经稳定过
> 一个去抖周期"，一次触碰后 ~20 ms 内它又饱和了，对"手指正按着"**完全免疫**。
> 两条判据看的是**不同的事实**，不能互相替代；**只看 `cnt` 就等着吃假 PASS/假 FAIL**。

**其它要点**：

- **元素步长用 `sizeof`**（含尾部填充），不能用"最后一个成员的 offset + size" ——
  差那几个填充字节会让后面几个元素整体错位，读出来的"乱值"被误判成"内存被写坏"。
- **索引从 ELF 的枚举取**（DWARF `DW_AT_const_value`），不要手抄 `START=0,STOP=1,…` ——
  枚举增删/换序会让脚本静默写到**另一个键**上，判据照旧全绿（假 PASS）。
- **组合键必须专门测"与单键功能的冲突"，且要在边界测**：非边界处两个方向的增量会
  相互抵消，把冲突掩盖掉（实例：某两个键同时又是"参数 ±1"，在量程**端点**只有一边能生效
  ⇒ 组合操作完，参数悄悄偏了一个步长，页面完全看不出来，只有回读才发现）。
  所以用例要包含：**端点上做组合操作 + 读回参数不变 + 同时确认组合功能真的生效了**
  （别把"没触发所以没副作用"当成通过）。
- **多种触发路径必须收敛到同一个 API**（物理键 / 串口命令 → 同一个函数），
  验收时要**两条路径都测**，否则会漏掉"按键能、命令不能"这类分叉。
- 收尾**把伪造的状态复位**，别把设备留在"某个键一直按着"的状态里。
- **跨会话拼出来的按住**（`按下 → host sleep → 读状态 → 松开`，为了在按住期间读状态
  不得不拆成多次会话）**取不到会话内见证** ⇒ 只能在**松开之前**单独量一次见证量，
  并把它拼进 FAIL 详情（显式写明"未达时长 ⇒ 按键被物理触碰过，本条不是固件缺陷"），
  否则报告会把环境干扰指向固件。
- **读窄字段的地址必须先对齐再去重**：`mdw` 只吃 4 字节对齐地址，喂未对齐地址时
  sysprogs 版会打印 `0x…: ERROR 0` **且不报错退出** ⇒ 症状是"读回缺了几个字段"，
  与"探针连不上"完全不同（很容易往错处查）。按 `off & ~3` 收敛成对齐字、**去重**，
  再按 lane 取字节；顺带把"同字多字段"的读次数压下来。

### 7.8 ★「按住 N 毫秒」只能用**单会话目标侧计时**

想验长按 / 连发 / 双击这类**时间相关**的输入，很自然会写成
`key_press() → time.sleep(1200) → key_release()`。**这是错的**：如果 `key_press()` /
`key_release()` 各自起一个 OpenOCD 进程（一次会话 `init→halt→mww→resume→shutdown`
要 0.3~0.6 s），那么两次注入之间**目标 CPU 一直在自由运行**，
"按住时长" = 两次会话的真实墙钟间隔 + 两个会话自身的耗时 —— 抖动几百毫秒，
**与连发延迟（典型 600 ms）同量级**，判据直接失去意义。

**正确姿势：把计时搬到目标侧，一次会话内完成。**

```
init → halt
  mww(稳定位 = 1, 边沿锁存 = 1)        # 按下
resume
sleep(<ms>)                              # ★ 这一段由目标自己数，主机不参与
halt                                     # 时基由目标 CPU 的 SysTick 计，误差 = 会话开销之外几乎为 0
  mww(稳定位 = 0, 去抖计数 = 0)        # 松开
resume → shutdown
```

要点：

- **主机 `sleep` 只负责"让目标跑多久"**，真正的"按住了多久"由**目标自己的时基**度量
  ⇒ 主机调度抖动不进判据。
- 采样间隔要比被测周期**小一个数量级**，否则量化误差吃掉判据：
  连发周期 200 ms ⇒ 采样 / 判定粒度要在 ~20 ms 级。
- **期望增量的绝对时间轴派生**：长按总增量 = `1 + (held − DELAY) / PERIOD` 个连发步，
  而不是"每拍 +1"。主循环某些拍被阻塞式外设采样 / 串口打印拉长到几十毫秒时
  **会丢拍**，"数拍子"的模型必然对不上；用**墙钟绝对时间轴**才对。
- **两种步长并存时不要建第二本账**：短按步长 ≠ 长按步长时，"总增量 = 步数 × 某一步长"
  本身就写不出来。判据直接建模**总增量**（`expect_gain()` 返回一个数），
  容差取**一个连发步长**（容许最后一次连发的落点差异）——
  两本步数账必然有一本先过期，且过期时报的是"固件不对"。

### 7.9 ★ 写**基准量**合成传感器输入（无物理激励也能验阈值逻辑）

带传感器的板子上，凡是有"零点 / 基准 / 偏置"这类**可写**标定变量的，都能反过来用：
被测值通常是 `value = (raw − baseline) × per` 的差动式，**`raw` 读不出来但 `baseline` 写得进**
⇒ 写 `baseline` 就能把被测值**合成**到任意值，不需要压力源 / 砝码 / 信号发生器。

前提：**`per`（换算系数）必须能从真值源解析到**，且**量纲别搞错**
（本项目压力走 **µV(int32)**，写 nV 会溢出；分压 / 放大倍数藏在别处时要一并核对）。

**三条纪律，缺一条就会得到"看起来合理实则错"的结论：**

1. **必须闭环逼近，不能开环一次写。** "写 → 读回"之间存在
   `0.6~0.9 s`（会话开销 + 采样周期），期间**真实输入一直在漂**。
   本项目实测 AD7193 漂移 ≈ **620 码/秒**（≈ 8.4 cmH2O/s），
   而阈值就在 5.0 / 6.0 cmH2O 附近 ⇒ 开环写一次会带着 **5~7 cmH2O** 的误差落在阈值另一侧，
   用例"通过"或"失败"都是假的。
   做法：`for k in range(tries): 写 → 读回实测 → 未进容忍带则修正后再写`。

2. **修正量要含"自学习偏置"，否则迭代永远差一个常数。**
   若"写完到读到"的滞后 × 漂移 = 常数 `D`，那么 `achieved = target + D` 就是**不动点**
   —— 无论迭代多少次都差一个 `D`。修法：从第 2 次起，把**实测残差折算成基准偏移**
   加进写入量（`bias = (cur − target) / per`，`write = base − target/per + bias`），
   两次即收敛。**看到"迭代 N 次仍稳定差同一个量"，先怀疑滞后 × 漂移，不要加大迭代次数。**

3. **"输入确实落在预期侧"必须是独立的前置判据。** 容忍带要显式传参、
   且**验回差带（死区）内的用例必须收紧到小于半个回差带**——
   默认容忍 1.5 单位而回差带只有 1.0 单位时，用例会落在带宽两侧任意一侧，
   结论随机。同理，把带内用例的**两侧都测**（已封锁的一侧查恢复阈值、
   未封锁的一侧查切断阈值），两侧结论应当**相反**才是真判据；
   若两侧结论相同，说明判据退化成恒真。

**附带坑：窄变量可能地址未对齐。** `uint8_t` 旗标常落在字的中间字节
（实测 `0x20000210`），直接按字节读会 `Failed to read memory`
⇒ **先对齐到所在字整字读 `mdw`，再按 lane 取**（见 §7.1 的对齐说明）。

### 7.10 ★ 比"一次调试会话"更短的瞬态窗口：单会话采一排点 + 形状判据

**问题形状**：被测行为只持续 ~200 ms（启动补偿、软启斜坡、预置窗口、锁存刷新），
而**起一次调试会话本身就要 0.3~0.6 s**（`init → halt → 读写 → resume`）。
"打开会话 → 注入命令 → 读一次"读到的是窗口**之后**的稳态；
而稳态若恰好等于指令设定值，判据会**看起来完美通过**（恒绿）。

**做法一：把采样搬进同一个会话。**
会话打开后先注入被测命令（往 shell 命令环形缓冲里写字符），再循环
`短睡 → halt → 读状态 → resume` 采 N 次，序列连同 `t_ms` 一起带回。
`resume` 之后目标自由运行，`短睡` 的量级决定采样间隔（实测取 30 ms × 10 点，
覆盖 ~300 ms，足以横跨一个 200 ms 的窗口）。
**必须连相位 / 模式字段一起读回来** —— 只读输出值分不清"补偿中"与"已切回"。

**做法二：判据从"逐点等值"降级为"形状判据"。**
采样时刻不可能精确命中每一拍，判据只能是对**序列整体形状**的断言：

| 形状判据 | 对应机制 | 功能失效时的表现 |
|---|---|---|
| 序列里**存在**某点相位 = 补偿态 | 补偿阶段真的发生过 | 一次都没进入 ⇒ 红 |
| **峰值** > 设定值 | 确认阶段的目标确实是补偿值 | 全程 ≤ 设定值 ⇒ 红 |
| **末点** == 设定值 | 真的切回设定值，而不是停在补偿值 | 末点 == 补偿值 ⇒ 红 |

三条各自指向**一个可证伪的机制**，缺任何一条都会漏掉一种失效模式
（只测末点会漏"压根没补偿"；只测峰值会漏"补偿完没切回来"）。

**★ 顺带抓到的坑：沿判据的比较对象。**
序列里会出现「相位**已翻转**、目标**仍是旧相位值**」的一点 —— 这不是噪声，
而是"相位翻转发生在同一拍内（先按旧相位选目标、之后才翻转相位）"的直接证据
（实测点列：前 4 点 `相位=补偿态, 目标=补偿值`，第 5 点 `相位=已翻转, 目标仍=补偿值`，
第 6 点起 `目标=设定值`）。把退出条件写成 `输出 >= 本拍目标` 的实现，
会在第 5 点恒真 ⇒ 窗口在转换拍关闭、输出被**永久钉在补偿值**。
对症：**退出条件与"设定值"比，不与"本拍目标"比**；
验收侧别把这一点当抖动过滤掉 —— 它是判据坑的活证据。

## 八、★ 验收脚本自己的"元验收" —— 退出码语义必须打桩钉死

**踩过的坑**：一个"运行态验收"脚本复用停机态脚本的 `main()` 做逐像素比对，
收尾时写 `return rc if ok else 1`（`rc = V.main()`）。结果真机内容全 PASS，
脚本却 `exit=1`。

根因是 Python 的一条语言事实：

```python
sys.exit(True)   # 退出码 1（被外壳当成失败）
sys.exit(False)  # 退出码 0（被外壳当成成功）
```

`V.main()` 返回的是**布尔**（因为停机态脚本自己是 `sys.exit(0 if main() else 1)`），
把它直接交给 `sys.exit` 就得到 **PASS 报 1、FAIL 报 0** 的**语义倒置** ——
后者尤其危险：真失败被一键脚本当成功放过去。

**规则**：

1. 复用别的脚本 `main()` 时，**先看它返回 int 还是 bool**，再显式映射：
   `rc_ok = bool(V.main())` … `return 0 if (rc_ok and ok) else 1`。
   同仓库里返回 int 的脚本（`return 0 if nfail == 0 else 1`）不受影响 ——
   所以这类 bug **不会全仓库一致地犯，只会漏在那一个文件里**，逐文件核对退出点。
2. 核对方法：`grep -n "^if __name__\|sys.exit" tools/verify_*.py` 看每个脚本的
   出口，再对 `main()` 的 `return` 语句确认类型。
3. 四种组合穷举打桩（**不碰硬件**，秒级）——把 `inject`、被复用脚本的 `main()`、
   收尾函数全部换成桩：

```python
def run(vret, stopret):
    R.inject = lambda *a, **k: None
    V.main = lambda *a, **k: vret          # 比对成败
    R.stop_and_verify = lambda *a, **k: stopret
    sys.argv = ["verify_ui_running.py"]    # 让 argparse 走默认值
    return R.main()

for name, vr, sr, exp in [("PASS+停机成功", True,  True,  0),
                          ("FAIL+停机成功", False, True,  1),
                          ("PASS+停机失败", True,  False, 1),
                          ("FAIL+停机失败", False, False, 1)]:
    assert run(vr, sr) == exp, name
```

   打桩的前提是脚本内部**通过模块属性动态查找**被复用者（`V.main()` 而非
   `from ... import main`），否则 patch 不生效 —— 这也是"脚本内一律用 `import X`
   再 `X.f()`"的一个实际理由。

4. 修完后**真机重跑一次**确认退出码翻转过来（本次即 1 → 0）；打桩只证映射，
   不证真机路径。
