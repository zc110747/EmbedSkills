# 字节/舵机层链路（串口 + 固件）

## 0. 先分清"谁在说话"：协议分层

**这是所有串口误判的根源** —— 上位机与固件说的**不是同一层**。

| 层 | 词汇 | 谁实现 |
|---|---|---|
| **舵机级**（真机固件只有这层） | 舵机角设置/直控、摇杆、红外、复位、状态查询、统计查询、自动/停止/序列、硬件直读类 | 固件 |
| **关节级**（更上位概念） | 关节角指令、状态快照 | **上位机（后端翻译层）** |

★★ **固件侧可能根本没有关节级动词** —— 若协议文档自己写着"固件侧某动词仍待实现"，
就按这个事实推理，别照理想的协议文档假设固件会回状态。

★★ **"状态帧是谁发的？" 多半是"上位机自己合成的"。**
合成只发生在**上位机自己发起**的少数路径上：下发关节级指令（拆成舵机级指令，
收齐各轴回执后合成）、主动发状态查询、发复位（读回第二行状态）。
未识别动词的分支只**原样转发、不合成任何关节级回执**；被动收到的行只记日志。

⇒ **没有外部动作时，链路一定静默**。"静置 N 秒没有新状态"是**预期行为**，不是断线。

★ **关节级"指令回显"不是状态**：它是**目标**舵机角（**意图**），只用于核对标定。
拿它当实际值回推 ⇒ **误差恒为 0**，把「滞后 → 收敛」整条语义抹掉。
★ 舵机级回执是**钳位后**的目标角，状态帧/硬件直读才是**实际角**；
三者形状都含同一套 `键=值` 片段 ⇒ 必须靠**前缀白名单**分流，否则"状态永远等于命令"。

★ **摇杆 / 红外改完舵机角不回吐任何东西**（真机固件行为）⇒
"用摇杆动一下，看上位机跟不跟"在**纯串口链路**上得靠**上位机主动轮询**或**固件主动上报**，
不能指望设备自发。★ 而后端通常**只在暖机时发一次状态查询**（目的是纠正
"开串口复位 ⇒ 舵机弹回 HOME"造成的显示失真），**之后不再轮询**。

## 1. 关键坑清单

> 若这些编号会被代码/文档引用，则**改编号必须全仓同步**；检索词与引用点要随重构一起更新。

| # | 坑 | 一句话 |
|---|---|---|
| **1 / 2** | **复位窗口吞指令** | 开串口拉低 DTR ⇒ 复位；横幅**前、后各吞一条**且**不回执** ⇒ 就绪判据 = "**能应答**"，不是"看到横幅"（详见 §3） |
| **3** | **摇杆必须保持增量模型，勿改绝对定位** | 摇杆是**增量/速率**语义：朝某方向累计增减、松手停在原地，**位置与角度无映射关系**。曾把"转角比参考实现小"误判为"应改绝对定位" ⇒ 被用户纠正并 revert。★ **涉及模型/语义的改动，先确认需求模型，别凭"参考实现用了某种映射函数"之类臆测动手** |
| **4** | **脉宽标定才是"角度偏小"的真因** | 小舵机满量程 ≠ 通用 `1000–2000µs`；按中段映射会把**物理行程压到约一半**。且要与参考实现的脉宽对齐（**含"中点不是 1500µs"这类细节**）。★ 归因顺序：**先查脉宽标定，再怀疑摇杆模型** —— 本轮就是先改错了摇杆模型 |
| **5** | **串口空闲 N 秒后假性断连** | 用通用 `bufio.Reader` 读串口：Windows 空闲时 `ReadFile` 返回 `(0, nil)`，bufio 连续空读达阈值后抛 `io.ErrNoProgress` ⇒ **空闲必断连**；而重连会拉 DTR ⇒ **设备复位**。修法：**手写行缓冲**，把 `(0, nil)` 当作"暂无数据" |
| **6** | **不要轮询、不要排队** | 周期查询会**饿死遥控流**（挤占带宽 + 门控窗口）；门控在途时新命令**只覆盖"待发槽"**，**排队**会让拖动时命令无限堆积 |
| **7** | **Windows 非重叠串口 I/O 读写互斥** | 读线程常驻阻塞在 `ReadFile`（长超时）时，**并发 `WriteFile` 会被挡到读返回为止** ⇒ 每条指令的延迟 = 读超时量级。修法：读超时改"**立即返回**"模式 + 空读 `sleep` 短时间让出管道 + 广播写**放到锁外**（防半死连接持锁阻塞） |

**坑 6 细则**（同源：**周期查询会饿死遥控流**）

- 在 115200 波特率 + ACK 门控下，**周期查询挤占带宽与门控窗口** ⇒ 交互指令的回执**永远在追赶历史**。
- **latest-wins，不排队**：在途期间的新命令**只覆盖"待发槽"**。
- ⇒ 需要状态就用**变化触发上报**，或**极低频**查询；**别用轮询**。

★ **归因纪律**（坑 4 的教训）：同一症状有多个候选根因时，**先排掉"与参考实现不一致的常量/标定"，
再动模型**；改动模型前先向用户确认需求模型。

## 2. ★★ 唯一可信判据：独立计数器，不是收发对账

| 判据 | 可信度 | 说明 |
|---|---|---|
| 固件自报的**丢字节计数** | ★★★ **一票否决** | 链路真丢字节 ⇒ 必然非 0；**独立于上位机收发时序** |
| 状态帧**回读目标** | ★★★ | 证明"固件确实接受了目标"，不是只收到指令 |
| 脚本的"发送 vs 回执"对账 | ★ | **极易被工具自身的度量缺陷污染**（见 §3） |

⇒ **铁律**：要否定"链路丢字节"这一假设，**只能**靠固件的独立计数器；**不能用脚本对账**。
⚠️ 饱和计数：读到计数上限值别当"恰好这么多"（可能已经绕回）。

## 3. ★★ 诊断脚本的度量陷阱（写任何串口工具都要查这 4 条）

1. **"缓冲里还有整行"却被判空**：若取行函数只在"**新串口字节到达**"时才可能返回，
   则缓冲里躺着几百行而串口暂时安静 ⇒ 空转到超时返回空值 ⇒ 排空函数的**空闲判据被假空值
   触发、提前收工**。
   ⇒ **修法**：进循环前先查"缓冲区是否已含完整行"，**有就直接返回、完全不碰串口**。
2. **声称 fire-and-forget 实则逐条 `wait_for`** ⇒ 压力降到"发一条等一条"，
   且迟到的回执被塞进"其它"桶而报告**从不打印** ⇒ **静默吞掉**。
3. **只填"回执行内容"不填"回执耗时"**，而缺失统计读的是耗时字段 ⇒ **恒定**误报"全帧无 ACK"。
4. **拿固定等待窗口当就绪判据** ⇒ 见 §4。

> 与"自研解析器"同源：**工具的局限会被表现成数据的性质**。
> 自研工具给出**否定性结论**（"缺 N 条"/"文件坏了"）时，**必须先用独立手段复核**。

## 4. ★ 板子复位后的「吞命令」窗口（AVR 类 MCU + USB 串口，可复用）

打开串口会拉低 DTR ⇒ **复位**。实测：复位横幅（`... ready` 之类）要 ~1.6s 才来，
而**横幅之前、横幅之后各吞一条命令**，之后才稳定。

★ **`DTR` 边沿并非每次都触发复位**（连续开关端口时尤其如此）
⇒ **"是否看到横幅"不能当就绪判据**。
**唯一可靠定义是"能应答"** ⇒ 用**重试探针**（反复发一条轻量命令直到收到回执）。

**不是固件缺陷**：主循环非阻塞（每轮都跑命令轮询），是复位后 UART 的稳定窗口。

⇒ **实测脚本必须在单次连接内完成 `[设定位姿 → 稳定 → 抓拍]`**（关掉再开会再复位一次，舵机弹回 HOME）。

## 5. 真机链路约定（每次都要现场确认，别信记忆）

| 项 | 事实 |
|---|---|
| **串口号不是常量** | 随 USB 枚举变（如 COM 号递增），旧值会变成"`Present=False` 的幽灵条目" ⇒ **唯一改动点是配置文件里的端口字段**；先枚举一次实际端口再动手 |
| 开局位姿 | 固件开机多在 HOME；**开串口复位会把舵机弹回去** |
| 握手/hello 字段 | ⚠️ **字段可能缺失**（文档漂移）⇒ 判真机只能看**设备类型**字段这类稳定标识 |
| 握手与状态帧的到达顺序 | 同时到达且握手在前 ⇒ **发送点必须在收齐状态帧之后**，否则"保持不变"的关节会 fallback 到 HOME = **把臂拉回 home** |
| "保持不变"参数 | 会让状态**跨实验累积** ⇒ 对比实验**必须先回 HOME** |
| **串口独占** | 摇杆网关与后端**不能同时连**（Windows 串口独占）⇒ 此时界面不是"不跟随"，而是**根本连不上设备**；报错文案通常也写了"端口可能被其它程序占用" |

## 6. ★★ 验收口径：两条独立证据链，不能混着读

| 证据链 | 能证明 | **不能**证明 |
|---|---|---|
| **链路层**（设备类型 = 串口 / 指令回执 / 关节状态帧 / 无相机版 e2e） | 指令**确实送到了固件并被接受** | ❌ **物理到位** —— 真机无位置反馈，状态是固件**内部目标值**（开环） |
| **相机**（反解肩/肘绝对角） | **物理**在哪（唯一外部地面真值） | —— |

⇒ **链路层全绿 ≠ "真机验证通过"。** 要判物理到位，必须让相机取景按测量规范就位
（白分割板 + 画面内标尺 + 正交侧视 + **锁死曝光**）**且人员离场**。

- 台面没就位时，**绝对误差含反解公共偏置**，**不可当机械精度读**；
  只有**重复性（同位姿两帧之差）**是干净的噪声底。
- 取景里连臂都没有时，**只能报"物理层未取到证据"**，别硬算。

## 7. 固件侧的改动原则（"不制造静默失败"）

- **发送不要忙等**：`while (tx_full())` 忙等会阻塞主循环 ⇒ **停止读 RX** ⇒
  可能丢**整条指令且无痕迹**。改为"丢字节 + 计数"更可诊断。
- **RX 环形缓冲满时必须计数**（原为完全静默）。
- **缓冲区尺寸要留余量**（高负载下高位波特率会偶发静默丢字节）。
- 上报/计数类命令要有**一票否决**语义（丢字节计数 = 0 才是"链路干净"的证据）。

## 8. 常见误判对照表

| 症状 | 先查这个（而不是先改代码） |
|---|---|
| "脚本说全帧无 ACK" | §3 陷阱 ③：是不是只填了行内容没填耗时 |
| "缺了 N 条回执" | §3 陷阱 ①：空闲判据是不是被假空值触发 |
| "上电后前两条命令没反应" | §4 复位吞命令窗口 ⇒ 改用能应答的重试探针 |
| "静置一段时间没有状态帧" | §0：逻辑上**本来就不该有**（无外部动作则静默） |
| "摇杆动了但上位机状态不变" | 真机固件不回吐 + 后端不轮询 ⇒ 需要上报通路，不是"跟随坏了" |
| "界面/链路全绿但机械臂没到位" | §6：链路层证明不了物理层 |
| "两边都能连上但一个没反应" | 串口独占（§5）⇒ 只能有一个持有者 |

## 9. Web 前端交互语义（摇杆 → 串口链路特征）

- **死区门控**：摇杆在死区内**不下发**任何指令（避免噪声刷屏），出死区才恢复下发；死区值集中在一处配置。
- **方向反相配置是分轴的，且可能有"两层"**（硬件固件对部分轴出厂即反相 + 配置/前端再反相）
  ⇒ 改方向前先确认**哪一层在反**，别把两层叠加后的结果当成一层。
- ★ **"按住不动"必须有心跳**：只在指针移动时发帧 ⇒ 按住不动舵机就停（交互拖沓）
  ⇒ 拖拽中按固定周期（数十 ms）**重发当前位**（对齐硬件摇杆扫描语义），松手停 + 回中。
- **状态查询是点击式**：周期轮询会饿死控制流（坑 6）⇒ 角度靠**应答里自带的值**合并刷新。
- **角度合并**：单轴应答只带一个轴 ⇒ 必须 **merge 进最近已知值**，否则会把其它轴显示成零。
- ★ **静态资源内嵌进二进制（`go:embed` 等）⇒ 改前端必须重新构建才生效**
  （构建产物与源码"看起来都在"，极易忘）。

## 10. 未闭合（如实保留）

- 真机"偶发不执行"曾修掉**一个确定缺陷**（下发失败即 `return` ⇒ 第二条命令根本不发；
  以及等待回执时把异步事件误当应答），但**用户描述的症状仍未在真机复现**。
  后续方向：旁听**真实前端**而非脚本复刻 · 追问"不顺畅"的**物理表现** · 考虑
  **舵机供电/电流（堵转）**这类非链路原因。
- 夹爪开合方向若仅来自**口述**，**没有相机判据** ⇒ 结论要标"待独立复核"。
