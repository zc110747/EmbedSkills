# 运行期配置门户的设计

## 1. 一句话原则

"运行期可配置"的本质是**同一份配置被多个执行流同时读写**：
驱动层正拿它收发数据、网页层正在改它、本地 UI 正在显示它。
绝大多数疑难 bug 都源自这一点（读到半截配置、改了没落盘、界面与实际不一致、非法值直达硬件）。

→ 先设计 **唯一真值源 + 串行化 + 白名单校验** 这三件事，再写业务代码。

## 2. 开工前先做三件事（省掉整轮构建周期）

1. **核对 SDK API 签名**，不要凭记忆写。大版本升级常伴随三类破坏性变化：
   符号被移除 / 结构体新增必填字段 / 旧 API 标成 `deprecated` 且默认关掉。
   逐个 `grep` 头文件确认签名与结构体成员，比"写 → 构建 → 报错 → 改"快一个数量级。
2. **评估分区余量**（见 §3）。
3. **定唯一真值源**（见 §4）。

## 3. 分区：加入网络协议栈后 app 体积会跳变

- 纯本地逻辑的固件 app 常只有几百 KB；**一旦链入 WiFi 协议栈 + HTTP 服务，体积会翻倍甚至更多**
  （协议栈 + TLS 库 + TCP/IP 栈 + 事件/网口抽象层）。
- 很多工程用的仍是默认"单 app"分区表，app 分区只有 1 MB。
  放不下的表现**不是运行期报错，而是构建后期才失败**（`app partition is too small for binary`）。
- 判断方法：构建后看 `*.bin` 的**实际字节数**，与分区表里该分区的 `size` 对比；留 ≥30% 给调试打印与后续迭代。
- 做法：换成自定义分区表文件（nvs + phy_init + 更大的 factory），
  并**同时改 `sdkconfig` 与 `sdkconfig.defaults`** —— 只改一处，重新生成配置时会被打回默认值。
- 顺手确认 flash size 配置与实际芯片容量一致，否则大分区在烧录/校验阶段就报错。

## 4. 配置的唯一真值源

- **只定义一次**：配置结构体 + 取值域白名单 + 「标签 ↔ 取值」互转函数，集中在一个头/源文件里。
  驱动层、网页层、本地 UI 层、持久化层**全部引用它**。
- 典型反例：网页拼 `"19200"` 字符串、驱动写宏 `19200`、UI 再写一份 `"19200"` 显示文本。
  → 加一个取值要改三处，漏一处就出现"网页能选、设备不认"。
- **枚举域要与被配置硬件的真实约束对齐**，不要收"任意正整数"：
  校验位只有 none/odd/even；停止位 1/2（1.5 只在 5 位数据下合法 → 直接排除）；
  波特率给显式白名单而不是范围。
- **派生值不要合并语义**：例如"没测过"和"测了但超时"是两种状态，
  合并成一个布尔会让上电默认界面看起来像整机故障。
  派生值继承输入源状态并定义明确优先级（差 > 未 > 好）。

## 5. 读操作与改参数必须串行化

- 现象：读到一半参数被改 → **偶发且不可复现**的失败；或改完参数后第一次读必错。
- 读操作往往自带超时（等总线应答，可达秒级），改参数又要触碰同一个外设 → 必须互斥。
- 正确顺序：**取锁 → 等发送 flush 完成（`uart_wait_tx_done` 之类）→ 重新配置 → 放锁**。
  不等 flush 就重配，会把正在发出的字节切成乱码。
- 锁要落在**驱动层**（`apply_cfg()` / `read()` 内部），别指望调用方自觉：
  网页线程与 UI 线程是两个独立调用者，**它们一定会并发**。

## 6. 网络输入校验：白名单，不信任网页

- 所有来自网络的取值先过白名单；非法值一律 4xx，且**不写持久化、不应用到硬件**。
- 边界最容易错：长度上限（8~63 是 63 不是 64）、枚举外的字符串、`"0"`、空串。
- 校验失败必须**可观测**：返回结构化错误（如 `{"err":"bad_param"}`），不要 200 + 静默忽略。
  静默忽略会把"改了没生效"变成无法定位的问题。
- 空值要有明确语义（例如密码空串 = 开放网络），别把空串一律当非法。

## 7. 配置持久化

- 首次上电无记录 → **用默认值并明确打日志**（`no stored settings yet, using defaults`），不要静默。
- 读回时**再校验一次**：记录可能是旧固件写的，或被人为改坏。校验不过就回落默认值并告警。
- 区分"已保存"与"已生效"：需要重启才生效的项（如热点密码），接口要如实告知调用方，
  **不要在保存时就假装已生效**。

## 8. 内嵌网页不要写成 C 字符串

- 用构建系统的资源嵌入能力（如 CMake 的 `EMBED_FILES` / `EMBED_TXTFILES`），
  拿到 `_binary_<basename>_start/_end` 直接当只读缓冲返回。
  - **符号名只取文件 basename**，路径里的目录名不参与；文件名中的连字符会被替换成下划线。
  - 需要精确字节长度时用 `EMBED_FILES`（二进制原样），`EMBED_TXTFILES` 会补结尾 `\0`，长度会算错。
- **不要内联成 C 字符串字面量**：一次转义错误就毁掉页面，
  而且会**把网页里的每个汉字喂给"源码字符集扫描器"**（见 §9）。
- 页面自报 `charset=utf-8`，源文件按 UTF-8 保存；响应显式带 `Content-Type: text/html; charset=utf-8`。

## 9. 界面文案改了，子集字库必须跟着重建

GUI 若用**子集字体**（只含从源码自动提取的那批字）：

- 新增任何汉字都可能缺字 —— **包括内嵌网页里的字**（如果扫描器把网页文件也当源码扫）。
- 缺字时 GUI **不会留白**，而是画**空心方框**并打 `glyph dsc. not found for U+XXXX`。
- 因此把"改文案 → 重建字库 → 跑覆盖校验（PASS 才算过）"写进流程，不要靠人记。
- 把内嵌网页**排除在扫描范围外**，可同时避免"网页文案污染字库"和"字库缺字"两个问题。
