# WebGL 首帧"重影"取证

## 0. 先分流：这不是一类 bug，是三类

看到"首帧多出一份东西、一交互就正常"，先判定属于哪一类 —— 三类的证据与修法完全不同：

| 类 | 现象 | 判据 |
|---|---|---|
| **A. 物体被画了两次，且变换不同** | 半透明副本错开，像重影/阴影 | 场景里同名根节点 **>1**；两个根的**世界坐标不同** |
| **B. 同一物体被画了两次，变换相同** | 只是偏亮/偏灰/边缘发毛 | 世界坐标**逐位相同**；`depthWrite=false` 的半透明叠加所致 |
| **C. 某一帧变换是陈旧的** | 一闪而过 | 逐帧记录里矩阵**在前若干帧是单位阵/旧值**，随后自愈 |

⚠️ **第一坑：截图抓不到瞬态。** `Page.captureScreenshot` 拿到的永远是**已经稳定**的那一帧；
"只在首帧存在、一动就消失"的现象，等到能截图时通常早已自愈（实测连截 10 张全是好的）。
必须在**每一帧**上留证。

---

## 1. 仪器一：渲染循环内的逐帧记录器

在渲染树里挂一个 dev-only 组件，在 `useFrame`（或 `requestAnimationFrame` 的渲染回调）里采样：

```js
// 记什么（每条都对应一个判定）
roots          // 场景中 name 前缀匹配的根节点数 —— >1 就是"画了多棵树"
perRoot = {
  transparent, // 由 material.transparent 判定，不靠名字（两棵树的名字往往完全相同）
  visible,     // root.visible
  origin,      // setFromMatrixPosition(root.matrixWorld)
  marker,      // 该树里某个已知标记点（工具端/中心点）的世界坐标 → 用它比较两棵树的位姿
}
```

**三条纪律（缺一条就会得到错误的结论）：**

1. **不要调 `updateMatrixWorld()`**。记录器在 `useFrame` 里先于 `gl.render` 执行，
   读到的正是**上一帧真正画出去**的矩阵；手动更新会把"矩阵陈旧"这类 bug 直接抹掉。
2. **正因如此，帧 0 读到的可能是单位阵** —— 那时还没有任何一帧被渲染过。
   若某个物体在帧 0 是单位阵、帧 1 就正确，那是**仪器伪影**，不是 bug。
   （实测：同一帧里主物体读数正确、副本在原点，只因主物体被另一条 `updateMatrixWorld`
   路径更新过 —— 差点被它带偏成"变换没被应用"。）
3. **上限封帧数**（如 900 帧 ≈ 15s），并只在读数**发生变化**时打印；
   逐帧刷屏反而看不见那两三帧的瞬态。

## 2. 仪器二：两张截图的平移对齐 + 残差

用户给的是"出问题前后"两张截图时，**先对齐再相减**，否则整页差异会把信号淹掉：

```python
# 互相关搜平移量，再取残差；残差的**空间分布**才是结论
best = min(((abs(A[y0:y1,x0:x1]-B[y0:y1,x0:x1]).mean(), dx, dy)
            for dy in range(-25,26) for dx in range(-25,26)), key=lambda t: t[0])
diff = abs(sub_a - sub_b).sum(axis=2)           # 残差图
for th in (60,120,200):                         # 多档阈值看**连通区域**落在哪
    ys, xs = np.where(diff > th)                # 落在物体上 ⇒ 物体被画了两次（类 A/B）
                                                # 落满全屏 ⇒ 相机/窗口变了，结论作废
```

⚠️ **第二坑：截图尺寸 ≠ 你看到的缩略图尺寸。** 按缩略图坐标去裁原图会**裁到空白**，
残差假性为 0 —— 这足以让你得出与事实完全相反的结论。先 `print(img.size)`，再按比例换算 ROI。

## 3. 复现：把前提摆到**数据源**一侧

瞬态复现不了，通常是因为**触发它的前提没被摆出来**。两件事必须做对：

1. **读代码找出两个输入的来源。** 类 A 的本质是"同一份几何被喂了**两组不同的输入**"
   （命令位 vs 实际位 / 期望值 vs 缓存值 / 服务端快照 vs 本地默认值）。
   把这两条链路各自追到**唯一来源**，问题通常就清楚了。
2. **去源头造前提，不要去渲染器里戳。** 若数据源**开机就停在一个固定值**，
   而页面把该值当默认假设 —— 那"刚启动就打开页面"这个条件**不足以**复现，
   必须**先把数据源挪到别处**再冷启动页面。写一个小工具做这件事
   （例：`<probe>.mjs` = 连上后端、下发目标、轮询到到位、断开）。
   **这类原语的副产品**：把"用户偶发"变成"可复跑回归"。

⚠️ 造前提时注意**端点不可精确到达**：限位端点经量化（整数度 / 0.1° 协议精度）往返后
可能落到限位外而被**如实拒绝**（`ERR <JOINT> ... (limit ...)`）。选**限额内部**的值当测试输入。

## 4. 修法取向：优先让两个输入**在源头一致**，不要靠隐藏第二个物体

| 方案 | 评价 |
|---|---|
| 让两个输入在源头一致（如接管链路时**以被控对象现状为命令起点**） | ✅ 同时修掉视觉 + "UI 显示假状态" + "首次下发是一记跳变" |
| 把第二个物体藏起来（默认关 / 首帧不画） | ❌ 假状态与跳变危险仍在，还**毁掉一个真信号** |
| 每次回推都写回命令侧 | ❌ 形成 `命令→状态→命令` 回环 |
| 首次连接就把本地命令发下去 | ❌ 会让被控对象一记跳变（危险），且改掉了既有时序契约 |

若采用"源头对齐"这一次性握手，**必须同时加两道护栏**：

- **不下发**：对齐只改本地参照，不能被"命令变化→下发"的订阅当成用户意图（用一次性抑制标志）。
- **让位于用户意图**：若第一帧回推**之前**用户已经操作过，放弃对齐 ——
  否则会把刚下达的意图悄悄擦掉。（这条是被"Mock 的 tick 比 connect 慢一拍"的真实测试失败逼出来的。）

## 5. 验收：改测试前先分辨"哪条不变量是刻意的"

唯一被改动的测试，往往是**故意钉住**某条契约的那一条（例："回推只写实际位、引用不变"）。
正确处理是把它**拆成两段**（握手一次性 + 稳态引用不变），钉子比以前**更强**；
而不是删掉或放宽它。先读测试标题与文件头注释，判断哪条是**刻意的契约**、哪条只是实现细节。

## 6. 最小检查清单

1. `print(img.size)` 对齐两张截图 → 残差落点是否在物体上？
2. 逐帧记录器装了没有？`roots` 是否 >1？两棵树的 marker 世界坐标是否相同？
3. 帧 0 的异常读数，是不是"还没渲染过"的仪器伪影？
4. 两个输入各自的**唯一来源**在哪？页面默认值与数据源开机值是否一致？
5. 复现脚本写了吗？它是否**先把数据源挪走**再冷启动？
6. 修法是否让两个输入在源头一致？两道护栏（不下发 / 让位用户意图）加了吗？
7. 被改动的测试，原来是**刻意**钉住哪条不变量？
