# replica-recon · 复刻前的逆向取证

> `replica-` 系列第 1 步。目标：**在写第一行实现代码之前，把"原件到底怎么做的"变成带证据等级的结论清单**。
> 后续：`replica-memory-engine`（运行期引擎）· `replica-ui-fidelity`（界面复刻）· `replica-mock-harness`（替身验收）。

## 何时用

- 拿到一个要复刻的第三方工具（exe/dll/安装包/脚本），准备动手实现。
- 不清楚原件的**行为边界**（哪些功能是改数据、哪些是改逻辑）。
- 内嵌了加密/打包的资源（皮肤、脚本、配置），静态提不出来。
- 需要向用户/团队说明"这条结论可靠到什么程度"。

## 铁律

1. **每条结论必须带证据等级**，并写进交付文档。三级：
   - `静态取证`：只读文件字节/结构得出（PE 解析、字符串、资源解码）。
   - `交叉互证`：≥2 条**互相独立**的证据指向同一结论（如符号表 + 调用点反汇编）。
   - `真机验证`：在真实运行环境中观测到行为符合预期。
2. **静态结论 ≠ 实现依据。** 静态只能给出"候选"，凡涉及解引用/地址/遍历序的结论，
   必须标注"待真机验证"，并在拿到环境后一次性钉死。
3. **不要相信单一证据。** 同一事实在字节、字符串、行为三处互相印证才算定案；
   只有一处就写明"孤证"。
4. **原件不可运行 / 会弹 UAC / 有反作弊时**，先做静态；动态观察需用户明确授权，
   且**只在离线单机**场景，不用于联机。

## 工作流

| 步 | 目标 | 产出 |
|---|---|---|
| 1 | 确认身份 | 编译器/框架/版本指纹、文件类型、是否加壳 |
| 2 | 静态解析容器 | 段表、导入表、资源表、重定位；导出为可检索的中间形式 |
| 3 | 资源与字符串挖掘 | 内嵌脚本/配置/标记/词条（含多语言）、密钥或编码线索 |
| 4 | 行为边界判定 | 每个功能归为「改数据」还是「改判定逻辑」 |
| 5 | 证据分级归档 | `结论 | 证据 | 等级 | 待验证点` 表 |

## 核心知识点

| 主题 | 结论 |
|---|---|
| 身份指纹 | 先看节名/导入表/资源类型；自绘 UI 的 `comctl32`+自绘类名、.NET 的 `mscoree`、Qt 的 `Qt5*` 都是强指纹 |
| 加壳判定 | 节表熵值异常高 + 导入表只剩 `LoadLibrary`/`GetProcAddress` ⇒ 加壳；**先脱壳再取证**，否则结论全是噪音 |
| 资源加密 | 加密资源**静态无法还原**；正确做法是"运行原件截图/抓内存"，而不是硬解 —— 且需用户授权 |
| 字符串编码 | 同一份数据可能同时以 ASCII 与 UTF-16 存在；两种都要扫，只扫一种会漏掉一半 |
| 多语言词条 | 词条常按语言分块连续存放 ⇒ 可用"相邻语言块对齐"反推条目数与顺序 |
| 内嵌脚本 | 脚本常以明文或"明文字符串表"形式存在；抓出后即可作为**实现规格**，比猜行为可靠得多 |
| 行为边界 | 凡"改判定结果"的功能（无敌/倍率/免疫类），本质是 patch 指令；凡"改数值"的功能，是读写字段。二者实现路径完全不同 |
| 版本耦合点 | 找出版本相关的占位/常量（版本号、签名通配、硬编码 RVA），它们是**换版本时唯一需要重校的东西** |
| 证据链 | 结论写"复合证据编号"（如 `E1+E2`）比写"经分析"有用得多；评审时能直接回查 |

## 反模式

- ❌ 只做静态就宣布"功能已对齐"——静态给不出遍历序、给不出运行期地址。
- ❌ 硬解加密资源：耗时且多半失败；正解是动态取证（需授权）。
- ❌ 用"原件行为看起来是这样"当实现依据却不标注等级。
- ❌ 只扫一种字符串编码。
- ❌ 把"原件内置了某模块/某 dll"当成"必须同样内置"——**先判断它是不是真的被这条功能路径用到**。
- ❌ 反作弊/联机场景下做动态观察。
