# MCU AI Agent 开发总方法论

核心结论：**AI 生成嵌入式代码不难，难的是「交叉编译 + 烧录 + 仿真 + 真机验证」的自我迭代闭环**，
以及给 Agent 一份能落地的任务上下文。本 skill 是入口，落地细节见
`embedded-verification-acceptance`（验收）、`mcu-debug-forensics`（调试取证）、
`stm32-build-and-scaffold`（工程骨架）等下游 skill。

## 何时用

- 让 AI Agent 从零构建一个 MCU 工程，或把新需求交给它迭代。
- 写提示词、规划 AI 开发流程、判断"卡住了该不该人上"。
- 评估某个工程是否具备"Agent 能自己构建/烧录/验证"的前提。

## 核心知识点

1. **环境先就绪，再谈生成**。工具链必须全部进系统 PATH（编译器、cmake + ninja、openocd、
   python），编辑器侧装好调试插件以支持单步仿真；USB 驱动只能由人预先装好。
   把"环境已就绪"这一事实写进提示词，让 Agent 自行配置并自检。生成的构建/调试文件
   **一律用相对路径**，否则换机器即失效。
2. **提示词四要素缺一不可**：功能需求 + 硬件信息 + 开发步骤 + 验证手段。
   直接说"帮我写个单片机程序"必然返工。已验证驱动、原理图、已验证参数**提供源码优先**，
   不要让 Agent 从零猜。
3. **先出计划再动手**：任何新模块动手前先出实现计划并获确认，不要直接写代码。
4. **分阶段交付**：先跑通最小可运行单元并验证，再逐步集成高级功能；每完成一个模块立即
   增量汇报，不要等全部做完。
5. **验收要数字**：Debug / Release 双构零警告、FLASH / RAM 占用、verify 脚本 pass/fail 计数，
   全部显式列出。无法验证的代码只是半成品。
6. **人对硬件的介入不可省**：设备未重新枚举、目标板掉线/供电异常、外部器件参数反复试错不收敛、
   接线归属不清——这些 Agent 无法自愈，需人及时出手。

## 判据与反模式

| 反模式 | 判据 |
|---|---|
| 期望 AI 写嵌入式"一步到位" | 必须分阶段 + 人工干预 + 真机验收 |
| 让 AI 从零猜外部器件驱动 | 提供已验证源码，效率高一个量级 |
| 以"生成完毕"当交付 | 只有跑通验证闭环才算完成 |
| 忽略编译警告 | 强约束双构零警告，警告即视为缺陷 |
| 环境没验证就下任务 | 先自检工具链可调用，再交任务 |

- AI 的能力**上下限都很极端**：复杂功能可以长时间连续跑通，也会在某个外设参数或构建入口
  上卡很久。卡住时优先补上下文（源码、原理图、现象），而非换更长的提示词。
- 硬件现状与代码不符时，先怀疑观测手段（烧的是不是新固件、串口有没有被占用）。
