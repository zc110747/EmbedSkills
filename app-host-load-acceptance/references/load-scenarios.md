# 规模压测的场景语义与陷阱

配套 `app-host-load-acceptance/SKILL.md` §2。每个场景写清：**断言什么、怎么构造、会怎么骗你。**

---

## 一、规模连接 + 扇出（每个 N 都跑）

### 构造

```
N 个客户端【同时】连接（每客户端一个线程）
→ 等成员数到位（DISCIPLINE A）
→ 从【索引最大】的那个客户端发一个带唯一标签的包
→ 断言另外 N−1 个都收到了它，且是"恰好命中某个包一次"
→ 读服务计数，断言聚合恒等式
```

### 为什么必须让**最后接入**的那个客户端发送

历史上"隐身"的正是它 —— 第 64 个及以后接入的客户端连接成功、被计入在线数，
但**服务从不读它**。用一个早期接入的客户端做发送者，会得到"完美"的假结论。
**发送者必须覆盖索引的最大值**（更彻底：抽若干个不同索引，含边界 ±1）。

### 断言清单

| 断言 | 强度 |
|---|---|
| `accepted == online == peak == N`，`rejected == 0` | 每个客户端相信的连接都成了成员 |
| 高位发送者的包被 N−1 个对端收到 | 边界问题 |
| `packets_out == 发送者数 × (N − 1)` **精确** | **聚合无损的证明** |
| 无拆包、无重复 | 一包一次 `send()` 的契约在规模下仍成立 |
| 容量溢出计数 == 0 | 没有套接字被**静默**拒绝 |

### 陷阱

- **`packets_in` 与 `packets_out` 不是一回事。** 一次大写入会被 `recv()` 切成多个包
  （实测：9000 字节写入 = 恰好 3 个包，4096+4096+808）⇒ 这证明分包依据是 `recv()` 返回，
  **不是内容**。别用"包数"推断"消息数"。
- **采样接收者**。N=1000 时对每个接收者都做完整比对是 O(N²) 的接收量，
  测试本身会变成瓶颈（而且并不比恒等式给出更强结论）。采样固定个数（如 8），
  并在文案里写明 `(sampled 8 peers)`。

## 二、突发连接（backlog）

### 构造

`N` 个连接**同时**发起（不是串行循环 —— 串行会在过程中把内核队列排空，**掩盖** backlog 过小）。

### 断言

- `refused == 0`（连接层面没有 `ECONNREFUSED` / `WSAECONNREFUSED`）；
- 耗时；
- 等成员数到位后 `online == N`。

### 陷阱

- **必须用同时并发。** 串行连接循环几乎不可能触发内核队列溢出，于是"测了等于没测"。
- **必须显式对比不同的 backlog**（或用启动告警），否则你不知道自己是"恰好够"还是"差一点"。
  实测：1000 突发在 `backlog=16` 下丢 63 个，`backlog=128` 丢 0 个。
- 突发之后**必须等成员数**再断言 `online`（否则读到 973/1000 的中间值）。

## 三、背压（一个停止读取的 peer）

### 构造

```
1 个"正常接收者" + 1 个"停止读取的 peer" + 1 个发送者
发送者持续发，直到服务把停止读取的 peer 丢弃
```

### 断言

- 停止读取的 peer **被丢弃、被计数**（`dropped` 之类的计数增加）；
- **正常接收者不受影响**（继续收到包）—— 这条比第一条更重要：背压必须是**按连接**的，
  不能一个慢 peer 拖垮其他人；
- 丢弃发生在 `out_buffer_bytes` 之后，而不是无限堆积。

### 陷阱

- 停止读取要**真的停止 recv**（而不是慢慢读）。在 Python 里最简单：根本不启动读取线程。
- 需要设**合理超时**：这个场景本质上依赖"缓冲区填满"，慢机器上要几十秒。
- 别把"被丢弃"当成失败 —— 它是**设计行为**。断言的是"被丢 + 被计数 + 不影响别人"。

## 四、连接抖动（泄漏）

### 构造

`K` 轮 × `M` 个客户端：连上 → 发一个包 → 断开。轮间不等待（也可以刻意做半开/立刻 RST）。

### 断言

- 结束后 `online` 回到**基线**（常驻客户端数）；
- 调度器/线程的**活跃任务数回到基线**（例：`active_tasks == 2`）；
- 帧计数平衡（`frames_created == frames_destroyed`）。

### 陷阱

- **必须等到"回到基线"再断言**，而不是"等一段时间"。用 `wait_for_counter`。
  否则会读到"还没回收完"的中间值，误判成泄漏。
- 断开的姿势值得变化：正常 `shutdown` vs 直接 `close`（发 RST）vs 半开。
  **RST 路径最容易暴露错误处理缺陷**（本仓就是在这条路径上发现日志吐出了本地化文本）。
- 泄漏断言要**两个维度**：连接槽位（`online`）与执行单元（`active_tasks` / 帧计数）。
  只查一个会漏。

## 五、优雅关闭

### 构造

满员状态下发停机指令（控制台命令 / 信号）。

### 断言

- **全部 N 个客户端都被通知到**（收到了停机通知字节）；
- 进程在 **X 秒内**退出，退出码 0；
- 无泄漏（`frames_balanced == yes`）。

### 陷阱

- **必须带超时的退出断言。** 只 `terminate()` 收尾会把"关机挂死"这个真实缺陷掩盖掉。
  实测反例：一个 detach 的控制台线程持有流锁，会让进程**永不退出**。
- 停机通知本身也会受 TCP 合并影响：断言"包含通知文本"即可，别断言"它是独立的一个包"。

## 六、贯穿所有场景的两条

### 1. 空转成本要量一次

1000 客户端连着、什么都不干时的 CPU 占用（实测 < 5% 单核）。
这是"每轮全量重建等待集合"这类设计的**真实代价**，不量化就无法判断是否要换 `epoll`。

量法：`proc.cpu_times()` 前后取差 / 墙钟 —— 比读任务管理器可靠。

### 2. 每次运行的 P/F 计数都要打出来

```
LOAD relay: PASS (104 checks)
```

数字变化本身就是信号：某天从 104 变成 96，说明**有检查没跑**（而不是"通过了"）。
这跟"断言要覆盖边界值"同等重要。

## 七、一份实测基线（可直接当"数量级对不对"的参照）

Windows / MinGW-w64 / GCC 15.2 / Release，单线程 `select()` 服务，`poll_interval_ms: 5`，
16 个发送者：

```
    clients  connected  refused  connect s  fan-out s  packets_out
        100        100        0       0.05       0.10         1584   = 16×99
        300        300        0       0.07       0.10         4784   = 16×299
        500        500        0       0.10       0.21         7984   = 16×499
       1000       1000        0       0.22       0.21        15984   = 16×999
```

- `connect s` 随 N 大致线性增长（0.05 → 0.22 s），说明 accept 没有退化成 O(N²)；
- `fan-out s` 在 500 之后**不再增长**（0.21 s 持平）—— 这是"单轮全量扇出"应有的形状；
  若它随 N 平方增长，说明扇出实现里有每对客户端一次的扫描。
