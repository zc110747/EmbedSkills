# 四类静默失败：逐条症状、根因与定位

LVGL 渲染层不报错：缺字形、值越界、区域被裁掉都是**安静地不画**，
而 API 层（`lv_obj_get_width()`、`lv_font_get_glyph_dsc()`）一切正常，单元测试全绿。
下面每条都给出「症状 → 根因 → 定位手段」，再给出可执行的判据。

## 一、速查表

| 症状 | 根因 | 定位手段 |
|---|---|---|
| **整屏有框无字**：容器、边框、颜色全对，一个字都不显示 | `lv_conf.h` 的 `LV_USE_FONT_COMPRESSED` 与字体生成器不匹配。生成器不加 `--no-compress` 时输出压缩位图，若配置里该宏为 0，`lv_font_get_bitmap_fmt_txt()` 返回 **NULL**，LVGL 对 NULL 位图直接不画 | 探针里逐码点检查 `lv_font_get_bitmap_fmt_txt()` 非空 |
| **某个字画成空心方框**（豆腐块）：子集字库缺字 | 该字不在字体的 cmap 里。LVGL v8.3+ 在 `LV_USE_FONT_PLACEHOLDER=y`（默认开）时画一个 `border_width = 1`、`box_w = line_height/2`、`box_h = line_height` 的空心矩形，颜色取文字色 —— 所以它**看起来像一个 UI 元素**（带色方框很容易被当成图标），**同时打 `LV_LOG_WARN`** | 最省事：`grep "glyph dsc. not found" console.log`。其次逐码点 `lv_font_get_glyph_dsc()` |
| **图表是一条线 / 什么都没有**（网格在，曲线不在） | 样本用 `lv_coord_t`（= int16）存，直接喂带小数的物理量会被四舍五入到整数刻度。跨度小于 1 个整数台阶的数据全部塌成同一个整数，轴范围退化成两个相邻整数，曲线压到绘图区最下面一行贴着边框 | 打印轴范围与缩放参数；看 plot 出来的整数值有几种 |
| **曲线顶端凭空消失** | 缩放后的值等于 `LV_CHART_POINT_NONE`（= `INT16_MAX` = 32767），LVGL 把该样本当「无数据」**跳过** | 断言轴上限远离 32767（钳在 30000 之类） |
| **曲线尾部（最后一个样本）没了** | 在绘图层按点数上限截断，切掉的是**尾部**；而尾部恰恰是最关心的那个点（如收盘值） | 点数上限必须 ≥ 一个数据窗口的样本数 |
| **浮动标签挡住曲线**（或反过来） | 没说清要「让位」：只把标签放到上层只解决「曲线穿字」，不解决「标签盖住曲线」 | 见第三节：给容器留 padding，绘图区会真实内缩 |
| **内容永远是旧的**（改配置必须重启才生效） | 事件到了、UI 也重建了，但重建时读回的模型**没被重新加载**（`reloadXxx()` 写好了却零调用）。UI 忠实重绘了旧列表 | 见第四节：逐跳核数据来源；`grep` 找「已写好但无人调用」的函数 |
| **重排 / 换序操作无效**（内容刷新了，位置不变） | 「是否重建」的判定只比**集合**，没**逐位比较**；纯重排被当成「没变」走了更新快路径 | 见第四节末：判定必须比「内容是否有效」更严格，位置也是状态 |

## 二、图表：`lv_coord_t` 是 int16 这件事

`lv_coord_t` 在 `LV_USE_LARGE_COORD` 关闭时是 `int16_t`，图表样本和 Y 轴都是它。
**直接喂带小数的真实量 = 四舍五入到整刻度。**

- 症状：小跨度数据（一天变化不到 1 个单位）所有样本截断成同一个整数，曲线塌成一条压在
  边框上的直线，看起来就是「什么都没画」；大跨度数据照常，于是很容易误判成
  「这个 bug 跟数据种类有关」，而不是跟**数值跨度**有关。
- 解法：**缩放整数域**。把数值线性映射到几千级台阶上：
  `plot = (value - origin) * scale`，`scale` 按数据自身跨度取 10 的幂（不低于 1）。
  这是线性映射，形状不变；只要图上不画数值刻度，就不存在标错刻度的问题。
  把这层映射写成**不依赖 LVGL 的纯函数**，就能用普通单测覆盖：
  - 每一个最小变动价位必须映射成不同的绘图值；
  - 曲线不得贴边（含跨度接近 0 的退化情况）；
  - 映射单调。
- **轴上限必须远离 32767**：`LV_CHART_POINT_NONE` 就是 `INT16_MAX`，
  值等于它的样本会被**静默跳过**。取 30000 之类的钳位值。
- **点数上限绝不能小于一个数据窗口的样本数**：在绘图层截断切掉的是**尾部**。
- **数据源不会在窗口结束时自己停下**（会继续发到窗口之后），解析层要裁到窗口结束时刻；
  否则「最后一个点」根本不是窗口结束时的那个值。

## 三、布局：绘图区就是 content area，padding 是真留白

想给图表内嵌一个浮动标签，必须先知道 LVGL 图表把图形画在哪：

```c
/* lv_chart.c */
x_ofs = obj->coords.x1 + pad_left;
w     = lv_obj_get_content_width(obj);
```

也就是说**绘图区 = content area**，`padding` 是**真实的、可用的留白**，不是视觉遮挡。由此：

- 标签本身放在**父容器**上（不要放在图表里：图表的子对象被限制在 content area 内，
  正好落在留白的内侧），用 `LV_ALIGN_LEFT_MID` 之类对齐。
- 给图表设 `pad_left = 标签占用宽度 + 间距`，曲线就只会从留白右侧开始画，
  **永远不会钻到标签底下**。
- **宽度按标签实测自适应**，不要写死：同一句前缀配不同位数的数值，标签宽度能差出几十像素，
  写死要么不够（仍然重叠）要么浪费画布。
- ⚠️ **`lv_obj_get_self_width()` 对 label 只返回文字尺寸**，padding 和 border 要自己加回去
  （或先 `lv_obj_update_layout()` 再用 `lv_obj_get_width()`）。
- 标签与线「同生同灭」：没有数据就不画线、也不留白，把整幅宽度还给曲线。
- 通用教训（不限图表）：**`lv_obj_align_to()` 的偏移在调用那一刻固化**，
  基准对象尺寸变了不会跟随；每次改完文本都要重新锚定。`lv_obj_align()` 不受此影响。

## 四、第四类：事件到了、UI 重建了，但模型没更新

症状与前三类不同：**屏幕上有东西，但内容永远是旧的**。典型表现是
「改完配置必须重启才生效」——而 UI 代码、事件总线、重建逻辑**全都是对的**。

```
事件总线 → UI.handleEvent(CONFIG_CHANGED) → refreshPage() → 读 model
                                                                ↑
                                                          这里还是旧数据
```

**根因**：重建时读回的数据源**没有被重新加载**。UI 忠实地把**旧列表**画了一遍，
所以看起来「什么都没发生」。关键在于：**「UI 收到了变更事件」≠「模型已经读到新值」**。

### 为什么这类 bug 特别难查

- 每一层单看都正确：事件发布了、回调注册了、`handleEvent` 有对应分支、页面重建了。
- 日志也会骗人：`rebuilding pages` / `rebuilt N cards` 照常打印，N 还是**旧**的数目。
- 单元测试全绿 —— 因为**没有任何一层是错的**，错的是**调用顺序与数据源**。

### 怎么定位

1. 从「用户操作」到「界面」**逐跳列出调用链**，标出每一跳的数据来源。
2. 找**「已经写好但没人调用」**的函数。这是本类 bug 最典型的指纹：

   ```bash
   grep -rn "reloadXxx" src/     # 只出定义和声明？→ 找到了
   ```

   一个 `reloadXxx()` 存在却零调用，通常意味着有人写了但忘了接线。
3. 对可疑的 manager，`grep -n "manager_->" app.cpp` 把**全部**调用点列出来看有没有漏。

### 怎么修（注意顺序）

在事件回调里，**先**重载模型，**再**交给 UI 重建：

```cpp
bus_->setCallback([this](const core::AppEvent& e) {
    // 顺序不可颠倒：UI 重建时会读模型
    if (e.type == AppEventType::CONFIG_CHANGED ||
        e.type == AppEventType::DATA_CHANGED) {
        if (manager_ != nullptr) {
            manager_->reloadData();   // ① 模型先更新
        }
    }
    if (ui_ != nullptr) {
        ui_->handleEvent(e);          // ② UI 后读取
    }
});
```

⚠️ **顺序颠倒 = bug 依旧**：UI 先跑就会读到旧数据，即使 `reloadData()` 紧接着被调用。
验证时**用日志时间戳钉死顺序**，两行必须在同一毫秒内且 reload 在前：

```
INFO [DATA]  list reloaded: 4 items        ★ 必须在前
INFO [UI]    config changed, rebuilding pages
INFO [MAIN]  grid rebuilt: 4 cards
```

### 附带一类：只在集合变了才重建，忘了「顺序也变了」

配套陷阱：页面用 `setItems(list)` 刷新时，如果「是否重建」的判定是
**比较元素集合**而非**逐位比较**，那么**纯重排**（同集合、不同顺序）会走「只更新内容」的
快路径 —— 卡片保持旧位置，却被刷上别人的数据。表现为「重排无效」。

```cpp
// ✗ 只看集合：重排被当成"没变"，卡片位置不动
// ✓ 逐位比较：位置 i 的元素不同 → 重建
bool same = (existing.size() == list.size());
for (size_t i = 0; same && i < list.size(); ++i) {
    if (existing[i] != list[i].id) same = false;   // 按位，不是按集合
}
```

判定标准：**当「更新内容」与「重建」的适用条件不同时，
判定函数必须比『内容是否有效』更严格** —— 位置也是状态的一部分。

## 五、「没测」和「测失败」被合并成同一个显示

比「画不出来」更隐蔽的是**画出来了、但语义丢了**：数据模型里只有一个
`bool has_value`，于是**「尚未测量」和「读取超时」在屏幕上都是同一个 `-`**。
操作者无法区分「还没触发这一步」和「触发了但设备没回」——而测试工装最需要一眼看出的
恰恰是这个区别。

- 症状：默认状态满屏红色 `-`，看起来像**整机故障**，实际只是「还没开始测」。
- 修法：把二值 `has_x` 升级成**三态**（`EMPTY` / `FAIL` / `OK`），派生量与判定**继承**输入的状态，
  规则写死为 `FAIL > EMPTY > OK`；汇总判定 `FAILED > EMPTY > REJECT > PASS`
  （**失败优先暴露，不能被「还没读」盖住**）。
- 判定标准的说法要落到文档里：**「空白 = 没测过，`-` = 测了但失败」**，
  否则下一个人会把两者当成一回事再合并回去。
- `重置` 按钮要把整行（含派生值与判定）打回 `EMPTY`，即「上电默认态」，
  这样「默认全空」与「失败显 `-`」两条规则互相印证，也顺手给操作者一个明确的回零动作。

## 六、验收清单（渲染与数据流部分）

- [ ] 字体：每个字体渲染非零像素；运行期字符逐个码点校验 cmap + 位图非零
- [ ] 图表：最小变动价位映射成不同绘图值；曲线不贴边框；轴上限远离 `LV_CHART_POINT_NONE`
- [ ] 图表：点数上限 ≥ 一个数据窗口的样本数；序列已在解析层裁到窗口结束
- [ ] 布局：浮动标签与线对齐；留白宽度自适应；无数据时留白复位
- [ ] 探针：连渲染两次证明留白；像素判定用谓词/预量化而非纯色；搜索范围避开圆角
- [ ] 数据流：外部改了配置后不重启即生效（用日志时间戳证明「模型先于 UI」）
- [ ] 数据流：列表的**顺序**变化也能触发重建（不只是数量/内容）
- [ ] 显示态：每一个显示态都单独出过一帧样张（空白 / `-` / 数值 / 通过 / 未通过 / 重置后），
      而不是只灌一组极限值
- [ ] 出样张人眼确认一次（数字对不代表看起来对）
