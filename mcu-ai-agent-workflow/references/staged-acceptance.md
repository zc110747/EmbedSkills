# 分阶段验收节奏与人工干预时机

## 端到端阶段节奏

```
需求确认（完整上下文：路径 + 硬件细节 + 验收标准）
   ↓  实现计划（先出计划获确认，再动手 —— 不要直接写代码）
   ↓  编码实现（app/ + bsp/ + tools/ 同步）
   ↓  Debug + Release 双构零警告  →  仿真/真机验证  →  verify 脚本 pass/fail  →  交付清单
```

- **任何新模块动手前必须先出实现计划并获确认**。
- 每完成一个模块**立即增量汇报**，不要等全部做完。
- 验收以**数字显式列出**：RAM / FLASH 占比、零警告、pass/fail 计数。
- 具体做法与判据（零警告构建、烧录、verify 脚本形态、交付清单模板）以
  `embedded-verification-acceptance` 为准，本节只给节奏。

## 各阶段判据

| 阶段 | 通过判据 |
|---|---|
| 需求确认 | 能复述出"实现什么、接了什么硬件、怎么算成功"三件事 |
| 实现计划 | 有可执行的步骤与阶段划分，且经确认 |
| 编码 | 分层不乱（应用 / 驱动 / 厂商库 / 第三方） |
| 构建 | 双构零警告，占用数字有记录 |
| 验证 | 仿真或真机有可观测现象；脚本给出 pass/fail 计数 |
| 交付 | 增量汇报 + 清单齐备 + README 已更新 |

## 必须人工干预的时机

嵌入式要交叉编译 + 远程仿真，以下情况 Agent 会完全堵死，需人及时介入：

- **USB 设备未重新枚举**：实现 USB 相关功能时未重枚举，可卡半小时（拔插 USB 线 / 复位）。
- **设备掉线 / 异常**：调试探针断开、目标板供电异常，Agent 无法自愈。
- **外部器件调试死循环**：复杂外设参数错，Agent 反复试错不收敛 —— 此时提供已验证驱动源码。
- **硬件接线确认**：多条线缆归属不清（烧写线 / 上行线 / 调试目标线）时，需人现场确认。
- **驱动与物理连接**：主机侧 USB 驱动、串口驱动安装，Agent 装不了。

## 常见认知误区

| 误区 | 真相 |
|---|---|
| AI 写嵌入式"一步到位" | 必须分阶段 + 人工干预 + 真机验收 |
| 让 AI 从零猜外部器件驱动 | 提供已验证源码效率提升一个量级 |
| 生成代码 = 完成 | 无法验证的代码只是半成品，跑通闭环才是迭代基础 |
| 警告无所谓 | 强约束 Debug / Release 双构零警告 |
| 卡住就换更长的提示词 | 先补上下文（源码、原理图、实际现象），再谈提示词 |

## 经验沉淀的分层位置

多工程仓库里把经验固定到下面几类文件（文件名按各仓约定，关键是**分层不乱**）：

- **总纲**：仓库根 `README.md`（工程索引 + 开发经验总结）。
- **硬件配置**：`document/` 下的硬件说明文档（每类板子一份）。
- **环境说明**：`document/support.md`（工具链与依赖安装）。
- **各工程提示词**：`<proj>/prompter.md`（可直接复制微调，是"给 Agent 的完整上下文"的存档）。
- **各工程说明**：`<proj>/README.md`（结构与约定）。

## 换平台时什么不变、什么要换

同一套方法论（环境就绪 → 计划 → 编码 → 双构零警告 → 真机/仿真验证 → verify 脚本 → 交付清单）
适用于任意 MCU 平台。**变的只是工具链层**：

| 维度 | 变化点 |
|---|---|
| 编译 | 交叉编译工具链不同（GCC 系 / arduino-cli / 厂商 SDK 构建系统） |
| 烧录 | 调试探针 + OpenOCD，或串口下载（部分平台不依赖探针） |
| 日志 | 串口周期打印 `[SYS]/[MEM]/[TASK]` 形式的运行态快照，便于脚本断言 |
| 外设方向 | 有的平台自带 Wi-Fi / USB Device，可拓展网络共享等方向 |
| 验收 | 完全一致：环境可构建 → 真机烧录 → 日志/命令断言 → 增量交付 |

平台专属配方见对应平台 skill（如 `embedded-windows-toolchain`、`esp32-platform-notes`、
`stm32-build-and-scaffold`）；RTOS 方向见 `zephyr-stm32-porting`。
