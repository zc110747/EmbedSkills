# 行为边界：改数据 vs 改逻辑

> **这是复刻计划里最关键的一次分类。** 分类错了，后面的实现路径全错。

## 两类功能的本质差异

| 维度 | 改数据类 | 改逻辑类 |
|---|---|---|
| 做什么 | 读写目标进程里的**字段值** | patch **判定指令**，改变程序分支 |
| 实现 | 符号 → 指针链 → 字段地址 → 读写 | 定址指令 → 装跳板 → 在跳板里改行为 |
| 版本敏感度 | 中（指针链偏移会变） | 高（指令字节会变） |
| 可静态验证 | 部分（链结构可静态读） | 几乎不可（需真机指令边界） |
| 崩溃风险 | 低（值域守卫即可） | 高（从指令中间切开即崩） |
| 典型例子 | 生命/属性/道具数量/坐标 | 无敌、倍率、免疫、隐身、锁定 |

## 判定流程

```text
该功能的效果是「某个数值变了」还是「某个判断的结果变了」？
├─ 数值变了            → 改数据类
└─ 判断结果变了
   ├─ 判断依据是数据字段 → 可能仍可用「改数据」达成（写该字段使其恒真/恒假）
   └─ 判断依据是运行时逻辑（碰撞、倍率、时序） → 改逻辑类
```

**关键中间态**：有些功能"看起来是改逻辑"，其实可以通过写一个字段达成
（如"无敌"= 让受伤值恒为 0，如果程序每帧重算）。
**但**这类做法常常不稳定（下一帧被覆盖）或对**错误对象**同样生效——
必须检查"这个写法会不会也影响敌人/非玩家实体"。

## 对实现计划的影响

1. 分类完成后，**按类分批实施**，不要混：
   - 改数据类：先做，可静态单测（伪造内存），风险低。
   - 改逻辑类：后做，**一次只上 1 项**，真机确认不崩、效果可见再上下一项。
2. **必须列出"表本身覆盖不到的功能"**：数据源只提供数据链时，逻辑类功能必须自研钩子，
   这属于**超出数据源范围**的部分，要单独排期并向用户说明。
3. 每一项都要定义**语义替换 vs 完全一致**：
   - 完全一致 = 与原件字节级等价（最理想，常不可得）。
   - 语义替换 = 用"部分字段恒为 X"近似原件行为；**必须逐项向用户确认是否接受**。

## 反模式

- ❌ 把"改逻辑"当作"改数据"来做，结果某些功能"看起来生效"但在关键场景失效。
- ❌ 不做对象判定就写全局倍率（对敌人同样生效）。
- ❌ 逻辑类功能一次性全上（崩了不知道哪个引起的）。
- ❌ 不区分"完全一致"与"语义替换"，交付时用模糊说法掩盖差异。
