# origin 语义：谁引起、谁跟随

适用面：**本页 ↔ 设备**的点对点链路（关节级 WS / 串口 / 任何"一台上位机 + 一台设备"的形态）
一旦要接入**第三方入口**，就必须先把这一节处理干净。

## 1. ★★ 跟随由 `origin` 决定；前端禁止猜

| `origin` | 含义 | 页面行为 |
|---|---|---|
| `command` | 本页自己发的命令 | **不跟随**（这是本页的意图，跟随会吃掉命令语义） |
| `device` | 设备侧自主变化（手拨 / 摇杆 / 调试直控） | **跟随 + 抑制回发** |
| `external` | **另一台上位机**经第三方入口下发 | **跟随 + 抑制回发**（与 `device` 同等对待） |
| 未知 / 缺失 | —— | **降级按 `command`**（**宁可少跟随**） |

★★ **跟随必须抑制回发**：否则每次设备上报都会反弹一条命令下来，
形成 `设备 → 上位机 → 设备` 的**对抗**。抑制的作用域只覆盖**那一次** `set`。

★★ **来源必须"随命令同行"**，**不能**等状态帧到了再从"在途命令"里取来源 ——
应答一到就会清空在途记录，而**后续的状态推进帧仍属于刚发出的那条命令**。
来源要和关节值一起存进"当前来源 / 待发来源"，随 `dispatch → send` 走；
**待发槽（pending）也要一起覆盖**，否则尾沿补发会用错来源。
单测要专门覆盖"本页命令在途时外部命令进待发槽"—— 它测的正是"来源有没有跟着命令走"。

## 2. ⭐⭐ 第三方入口绝不可以用"本页命令"这个身份

借用 `command` 的后果有两层：

1. **看得见的**：对端页面**只更新实际臂 ⇒ 幽灵动、主臂不动**。
2. **真正危险的**：对端**指令侧停在旧值** ⇒ 用户**下次动页面上任何一个控件**，
   会把**整组旧指令**一次性下发 ⇒ **真机跳回旧位姿**。

所以这不是"显示瑕疵"，是**两套上位机抢控制权**，必须修。

⇒ **通则：给"本页 ↔ 设备"的点对点链路加第三方入口时，入口必须在协议里标注自己的身份。**
"能驱动" ≠ "对端界面显示对了"。

**修法**：给外部入口一个**显式身份**（协议里新增 `origin` 值，或复用既有的"外部驱动"值），
对端前端把"外部驱动"与"设备自主变化"同等对待（跟随 + **抑制回发**，否则引入
`命令 → 状态 → 命令` 回环）。验收要同时断言：跟随**发生**、回发**没有**发生。

## 3. ⚠️⚠️ 两层 origin 闸门必须同时改

只改一处 ⇒ 表现为"后端标了、页面却不跟随"。

1. **对端传输层白名单**：传输层会把帧上的 `origin` 映射成前端内部字面量，
   常见写法是白名单 `env.origin === ORIGIN_DEVICE ? 'device' : undefined`。
   漏放行新来源时，帧到达业务层时 origin **已经是 `undefined`**，表现与"对端根本没标"完全一样。
   类型系统通常会顺手报 `TS2367: ... '"command" | undefined' 和 '"external"' have no overlap`
   —— 这是**有用的信号，别当误报压掉**。
2. **对端业务层**：新增来源分支，与"设备自主变化"共用同一个"对齐命令侧"私有方法，
   但**日志文案必须分开**：把外部入口报成"设备侧自主变化（摇杆/红外/手拧）"是对现场的
   **误报**，而那个日志面板正是排障时最先看的东西。

## 4. 对端界面的硬判据：用**对端自己的 dev 探针**，不要靠截图

数字孪生前端通常在 dev 构建下挂调试句柄，暴露命令侧关节角 / 指令侧末端位姿 / 实际侧末端位姿。
于是"主臂与幽灵是否统一"可以量化，**四条一起看**才既证明"动了"又证明"没回环"：

| 断言 | 判据 | 量级示例 |
|---|---|---|
| 命令侧跟随**真的发生** | 外部驱动后命令侧关节角变化 | 某轴明显换向 |
| 主臂**真的动了**（排除"两者都没动"的假重合） | 指令侧末端位移 > 5 mm | 上百 mm |
| 二者**统一** | `\|指令侧末端 − 实际侧末端\| ≈ 0` | mm 级 0 |
| 渲染侧交叉验证 | 逐帧记录里非幽灵根与幽灵根的末端**世界坐标**重合 | mm 级 0 |
| **回发被抑制** | 驱动后新增下行命令数 = 0 | 0 |

只统计一次往返是**不够**的：连帧的 `origin` 分布才是根因证据（例如"统计到的帧全部是
`command`、零帧 `device`"，就直接证明了"入口借用了本页命令身份"）。
零依赖 Node 就能取证：`new WebSocket` + 打印字段。

⚠️ **驱动量要按当前位姿反向选**：写死某个舵机角时，上一轮跑完残留的位姿可能**正好就是**
那个值对应的位姿 ⇒"驱动后位姿不变"⇒ 判据假 FAIL。改成先读基线再决定方向，
保证每轮都有确定的可观变化。

⚠️ **抓日志要认清通道**：来源提示常走页面自己的日志 store（落到页面的日志面板），
**console 里一个字都没有**。用 CDP 的 `Runtime.consoleAPICalled` 去抓会两个关键词全 false
—— 看起来像"文案写错了"，其实只是抓错了通道。

## 5. 与后端实现的分工

- **后端**：在协议里定义 `origin` 常量；控制器维护"当前来源 / 待发来源"，随命令一起流转；
  外部入口的每条写命令都显式声明 `external` 身份。
- **前端**：传输层白名单放行新来源；业务层按来源决定"是否对齐命令侧"；跟随分支里带抑制回发。
- **验收**：后端侧分段（来源标记是否正确随命令流转）+ 浏览器侧（主臂与幽灵是否重合、
  是否发生回发）**两边都要有脚本**，缺一边就有一半语义没被证。
