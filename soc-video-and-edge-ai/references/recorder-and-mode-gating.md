# 结果录制器与 AI 模式下发门控

适用：推流端把推理结果异步上报到服务端，服务端要**留存可离线重放**的记录，
并且支持前端切换 AI 模式（关 / 检测 / 姿态 / 其他）。

---

## 1. 模式下发门控：白名单不收 = agent 被自己拉回去

**症状（极具误导性）**：推流端日志明明打印 `ready: mode=<新模式>`，
**1 秒后**又打印 `model switched -> mode=<旧模式>`。
看起来像推流端"模式切换有 bug"，实际是服务端的模式白名单没收这个值。

**因果链**：前端把目标模式写库 → 推流端**轮询**服务端取目标模式 → 白名单校验失败
⇒ 写库失败（接口返 `400`）⇒ 库里仍是旧模式 ⇒ 轮询器读到旧模式并**切回去**。

**结论**：只要新模式不在服务端白名单里，**联合运行下这个模式不可能稳定** ——
所以"白名单放行"不是锦上添花，而是任何新模式的**第一件事**。

**排查动作**：拿到现象先 `POST` 一次新模式看 HTTP 码，不要先读推流端代码。
`400` 就是根因；`200` 才需要往推流端的轮询/重建逻辑里查。

## 2. 落库保真：存生产者原字节，而不是重新序列化

若录制器的目的是"离线重放标定/实验"，则服务端**不得改写**上报数据。

做法：解码时把子对象的**原始 JSON 字节**留在结构体里（自定义 `UnmarshalJSON` 保存
`append([]byte(nil), data...)`），`MarshalJSON` 直接吐回原字节，写库时落这段字节。
效果：上报端后续**新增字段**，服务端不认识也不会丢 —— 不需要两边同时发版。

**这条性质可以自证，别只写在注释里**：挑一个"服务端重新编码一定会改变"的格式特征
作为证据。C/C++ 侧常用定点格式化，例如 `0.00`、`[0.0000,0.0000,0.0000]`；
而绝大多数通用 JSON 编码器会把它们写成 `0`、`[0,0,0]`。
从库里取出的字节仍是定点格式 ⇒ 证明是**原样透传**，不是再序列化。

配套：同一帧的"最新状态行"与"录制的每帧行"放在**同一事务**提交，
避免出现"前端看到了但记录里没有"（或反之）——那会让两个消费者对"第 N 帧发生了什么"给出不同答案。

## 3. 会话切分：时间间隔与"目标离场"是两条独立判据

录制是**无损追加**（含未检出的帧），"会话"是**分析**的产物。切分规则要写成两条：

1. **未检出（`detected=false`）的行无条件结束当前会话** —— 那是"目标离开画面"的签名；
2. **相邻两行的时间差 > `gap` 才切分**，且用**上报端时钟**（PTS）而不是服务端接收时间。

两者**独立**：任何 `gap` 都**跨不过**第 1 条。否则"握住 → 松开 → 再握"会被合并成一次动作，
而"目标确实离场"这件事必须能切断会话。

- 用上报端时钟的理由：网络抖动/重发会让服务端接收时间看起来像"目标走了又回来"，
  这是分析**自己制造**的假象 —— 分析最不该做的事。
- 顺带要处理**时钟倒退**：上报端进程重启会让帧计数与 PTS 归零。倒退量超过 `gap`
  同样切断会话（"重启不是一段连续动作"）。
- `gap` 属于**分析参数**而非录制属性 ⇒ 列表/导出接口应接受按请求覆盖
  （`?gap_ms=`），非法值返 `400` 而不是静默回落 —— 静默回落会让"打错参数"
  表现为"会话数量莫名变了"。

### 3.1 导出必须带录制器**自己的**单调键（`frame_id` 不是键）

上面那条"时钟倒退"处理掉了**切分**，但没处理**消费者**。上报端每次重启
`frame_id` 与 PTS 双双归零 ⇒ 日志里这两者**会重复出现**。实测一份 33 分钟的真机日志：
`(frame_id=77702, ts=2591322)` 紧接 `(frame_id=1, ts=700)`，`Δ=−2590622ms`；
该日志共 **2 处**重启、`frame_id` 有 **13 个重复值**。

**后果**：若导出文件只带 `frame_id` / `timestamp`，下游离线分析按这两者排序或去重，
会把**两次运行交错**。切分本身没事（它按插入序 `id`），躺枪的是消费者。

**做法**：导出结构里补上录制表的自增主键（`id`），并在文档里写明
"这是本文件**唯一**在日志生命周期内单调的键"。加字段**不必**升级文件版本号
（只有 shape 破坏性变更才升）。

**最容易漏的一环**：只改了结构体，没改生成它的 SQL —— 测试必须断言
**`id` 出现在序列化后的文件里**，而不是只断言 Go struct 上有值。

**容量**：无损追加必然增长（8 fps ≈ 29k 行/小时）。要有行数上界 + 最旧先剪；
裁剪**放在写事务之外**（剪失败只多占空间，绝不能导致上报失败）。
`上界 <= 0` 关掉录制器，但**最新状态仍要照写** —— 前端读最新值不依赖历史。

## 4. 校验的取舍：结构性数据严格，枚举 token 宽松

| 数据类型 | 策略 | 理由 |
|---|---|---|
| 置信度等标量 | 夹到 `[0,1]`，去 NaN | 消费端不该为 `3.7`/NaN 做防御 |
| **位置型数组**（例：21 个关键点） | **长度不对就整段丢弃**，帧的其余部分保留 | 数组按固定关节表定位，长度不对意味着"每一项换了含义"，不是"差一点" |
| 枚举字符串（手势名、左右手、运动方向） | **不校验，原样存** | 让上报端能先加新取值、服务端后跟版；校验只用于展示层 |

**读取接口的 404 纪律**：未知的实体 id 返 `404`，不要返"空结果"。
返"0 条记录"会让"id 打错"看起来像"录制器正常但空"，排查时会往错的方向走。

## 5. 验证录制器时的四个陷阱

### 5.1 灌合成帧前先关掉真实上报端

录制表按**插入顺序**（`ORDER BY id`）排序。若同一个实体 id 下既有真机帧又有合成帧，
两者**不是同一时间基**，会互相插队并触发 §3 的"时钟倒退"规则。

实测：合成帧 `ts=500125/500250` 之间插进一帧真机帧 `ts=494697`（倒退 5428ms > gap），
**本该 1 个会话被切成 3 个**。规则没错，但验证脚本会据此得出错误结论、
去改没有坏的东西。

**做法**：灌合成帧前先把上报端切到"关闭"模式（它就不再上报），或改用另一个实体 id。

### 5.2 只跑进程内单测不能算"验证了部署形态"

单测走 `httptest` 时，路径参数、方法匹配、事务边界、串行化行为都可能与真实进程不同。
验收要**对正在跑的服务发真实 HTTP**，并至少覆盖一条**完整闭环**：

    上报 → 落库 → 列表 → 导出 → 清空

导出文件要验**逐位往返一致**（例：关键点数组 `==` 原数组），而不只是"字段存在"。
更硬的判据：取库里某条 payload 的**原文**，在导出响应体里做**子串匹配** —— 命中即逐字节保真。

### 5.3 调 `gap` 要往**小于帧间隔**的方向调，往大调看不出任何变化

真机帧间隔 p50 ≈ 128ms（8 fps）时，任何 `gap >= 200` 都会桥接整段连续检出，
于是"1000 / 10000 / 60000 / 600000"全给出**同样**的会话数 —— 看起来像"参数完全失效"。

实测（同一份日志）：`gap=30 → 2193` 会话、`128 → 697`、`200 → 195`、`1000 → 194`。

**先量帧间隔，再决定往哪个方向调。** 没量就去调参，很容易得出
"这个参数根本没用"的错误结论，然后去改没坏的东西。

### 5.4 生产者**不做边界 clamp** 的坐标，越界不等于 bug

若上报端把模型输出的关键点映射回像素时不 clamp（很多参考实现就是如此），
目标**贴着画面边缘**时就会有坐标落到画面外。别急着判定"映射算错了"。

**判据（不需要看图）**：看越界是否**只发生在某一个轴**、且值贴着**同一条边**。

- 两个轴**一起**越界、或散布在四周 ⇒ 怀疑映射/缩放算错；
- 只有一个轴越界且紧紧贴着某一边 ⇒ 目标本来就出框了。

实测：x 全部落在 `[0,1280]` 内，而 y 有 1070 个点 `>720`（画面高 720），
腕点本身就在 `y=742~756` —— 因为手是贴着画面底边举的，第二级裁切方块伸出了下边界。

**对下游的影响**：前端 overlay **不能**假设关键点 ∈ `[0,w]×[0,h]`。
canvas 自身会裁剪所以画面不错，但任何"求均值 / 求包围盒 / 判断是否在画面内"的
HUD 逻辑必须显式处理越界值。

## 6. 受控夹具：用「探针 camera」把不需要动手的部分全测完

判据来自一个具体事实：**创建 camera 常常只写一行记录，不去配置媒体服务器**。
先读一遍创建接口的实现确认这一点，然后就可以建一个**专用 id**、
精确摆放合成帧、读回来断言、最后删掉 —— 全程**不影响真实链路、不影响在线上报端**。
比"停掉上报端再灌帧"（§5.1）干净得多，因为根本不需要停任何东西。

用它做两件事：

- **落库保真的机械证明**：POST 一个带**未知字段**（哨兵）的对象，导出后断言
  该字段**原样存活**。这是唯一能证明"存生产者原字节"的检查 —— 比对字段名集合、
  比对已知字段的值，都证明不了：重新序列化会把未知字段丢掉，而已知字段当然还在。
- **切分规则的两个方向 + 那条不可覆盖的规则**，三组帧摆在精确时间点上：
  `t=0,5000` ⇒ gap=1000 切 2 段、gap=10000 合 1 段；
  `t=0,100,200` 中间夹一帧"目标离场" ⇒ gap=100000 仍是 2 段。
  在夹具上测，判据是**确定的**；在真实日志上测，结论取决于那份日志恰好长什么样。

⚠️ **不要拿跨天累积的日志去断言"把 gap 调大就会合并"**。§3 讲过边界有两条独立判据，
但这里要强调后果：跨天日志的边界**几乎全是"目标离场"边界**，任何 gap 都跨不过，
于是"调大 gap"看起来**毫无效果**，很容易被误判成参数坏了。真实日志只能用来测
"调小 gap 切得更细"这一半；另一半必须上夹具。

## 7. 有人参与实验之前，先用合成真值把分析工具自证一遍

只要实验需要人去配合（举手、走动、按顺序做动作），就必须先让**分析工具**在一个
**已知答案的合成输入**上跑通。否则实验时**工具切错段会被读成人做错动作**，
结论正好反过来，而你不会发现。

做法：给分析脚本加一个自检开关，造一段"已知动作序列 + 真实抖动"，断言算法输出的
主轴与符号全对。这个自检不需要任何硬件，可以长期留在仓库里防止以后改坏。

### 7.1 锚点型分段的三个失败变体（都实测过，且在真实数据上不可见）

| 变体 | 实测症状 |
|---|---|
| 锚点每帧跟随目标 | 追掉真实动作的 72% ⇒ **0 段**（会被读成"人没动"） |
| 用最近 N 帧均值重新居中 | 那些帧横跨回位斜坡，锚点偏中位 0.016 > 回位带 ⇒ **下一段永远合不上，吞掉后面全部动作** |
| 吸附但忘了清零"静止计数" | 此后每帧都吸附 ⇒ 锚点钉在目标上，峰值只有真实幅度的 20% |

正解：锚点只在**确认静止达到时长**后吸附，且**吸附后必须清零计数**。
另外要有**入场过渡跳过** —— 录制从"目标刚出现"开始，那一瞬的位移本身就是一次
"永不回位"的运动，会把第 1 个动作吃掉。判据是"找到连续静止窗口后才开始找动作"。

代价要写进文档：慢于 `回位带 / 静止时长` 的动作会被吸进锚点而不上报。
