# 替身与验收（replica-mock-harness）

复刻工具最大的验证困境：**目标程序不可分发、不可控、可能根本装不上**。
解决办法不是"跳过验证"，而是**自研一个替身（mock）**，让它具备与真目标**同构的内存布局**，
于是所有「地址类接线」都能在没有目标程序的情况下端到端跑通。

> 本 skill 提供**方法**，不绑定任何具体表结构。
> 替身的字段名、指针层次、AOB 字节串都必须来自你自己的逆向结论（见 `replica-recon`）。

---

## 一、何时用

- 复刻工具已完成内存引擎（见 `replica-memory-engine`），但**手上没有目标程序**
- 做完 35 项功能接线后，需要一条命令回答"到底哪些通了"
- 验收脚本 PASS/FAIL 数量反复变化，但**说不清哪些失败是环境造成的**
- 出现"改了源码但结果没变"（产物没重编 / 脚本跑的是旧 exe）
- 需要把"回读值对不对"从**单一证据**升级为**交叉核对**

不适用：纯静态分析（用 `replica-recon`）；只关心界面像素（用 `replica-ui-fidelity`）。

---

## 二、铁律

### 铁律 1 —— FAIL 只能用于「该成立却没成立」

这是本 skill 的核心。判据必须**三分类**，绝不能二分类：

| 判据 | 含义 | 典型场景 |
|---|---|---|
| **PASS** | 接线成立，且**值可回读核对** | 读地址→链路→写值→回读==期望值 |
| **FAIL** | **接线该成立却没成立** | 位点存在（AOB 命中）、桩具备、但读/写/回读失败 |
| **SKIP** | **环境不提供该位点** | 替身没布该桩；该功能依赖代码钩子但替身无钩子桩 |

**反模式**：替身只布了 5 条数据桩，却对 14 条代码钩子项记 FAIL ——
这 14 项在替身上**必然**缺失，FAIL 数量会随替身能力随意波动，
报告从此失去"读了能决策"的价值。

> **实证**：某项目按此修法后，`PASS=26 FAIL=0 SKIP=15`；
> 随后真机逐项验证，这 14 项 SKIP **全部 PASS** ——
> 证明它们确实只是"替身验不了"，旧实现记 FAIL 会报出 14 个假缺陷。
> 详见第五节。

**正确做法**：探针先回答"这个位点在不在"，再回答"接线通不通"。

```
探针结论 → Hit            → 继续走 arm/disarm，按结果记 PASS/FAIL
        → SiteAbsent     → SKIP（目标进程不含该位点）
        → NotImplemented → SKIP（功能尚未实现）
        → NotAHook       → SKIP（该 flag 本来就不是地址类）
```

### 铁律 2 —— 替身必须在用户态真实进程里布桩

**不要**用宿主进程内 `malloc` 假地址糊弄 —— 那验证的是"指针算术对不对"，
而不是"跨进程读写对不对"。替身必须是**独立 exe**，被测工具通过 `OpenProcess` 访问它。

- 桩地址取自**模块基址 + 固定偏移**（与真目标的相对布局一致）
- 最好让替身**把关键地址打印出来**，供验收脚本核对扫描结果
- 数据桩的**字段偏移与层次**必须照抄逆向结论，不能"差不多"

### 铁律 3 —— AOB 桩必须自检「命中自身」

替身里埋的字节串，其**用途就是让扫描器命中**。因此：

```
扫描结果 == 替身自己登记的桩地址   → 桩有效（说明扫描器 + 桩都对）
扫描结果 != 桩地址（或零命中）     → 桩埋错了 / 通配符展开错了
```

这条自检把"扫描器 bug"和"桩埋错"两类问题**当场分开**，
否则你会去改扫描器，而真正的问题在桩的字节串上。

### 铁律 4 —— Oracle 交叉核对：替身自己是第二条证据链

工具写值后回读成功，只证明"工具能读到它自己写的东西"。
**独立证据**必须来自替身侧：

- 替身**周期性采样**关键数值，输出 change 日志（`t=1.2s hp 100→9999`）
- 验收脚本把「工具回读值」与「替身采样值」对齐核对
- 两者一致才叫"真的写进去了"；只有工具回读 == PASS 是**孤证**

### 铁律 5 —— 产物新鲜度闸门：先比 mtime，再谈结果

"改了源码但结果没变"的根因几乎都是**跑的是旧二进制**。
验收脚本第一步必须：

```
产物 mtime > 所有源文件 mtime   → 放行
否则                            → 直接报错退出，不解释任何功能结论
```

同理：Debug 构建跑通 ≠ Release 构建跑通，**两套都要跑**。

## 三、核心知识点

| # | 知识点 | 要点 |
|---|---|---|
| 1 | 替身工程独立 | 单独目录 + 单独构建脚本，**不混进主工程**，避免污染被测产物 |
| 2 | 模块基址获取 | 替身自己 `GetModuleHandle(NULL)` 作为基址，偏移与真目标对齐 |
| 3 | 桩区集中 | 所有桩放在一个静态结构体/节里，便于一次性核对其布局 |
| 4 | 指针链桩 | 三级链就埋三块内存 + 中间存下一级地址，**末级存值** |
| 5 | 无引用根节点 | 只被指针链引用、本身不在任何全局符号里的节点，要**预先登记**，否则工具找不到根 |
| 6 | 数值类型 | int32/float/bool 分别埋，**对齐到 4 字节**，避免跨界读 |
| 7 | 位域桩 | 一个字节既存 flag A 又存 flag B 时，写入必须**只改目标位**，验收要覆盖"改 A 不动 B" |
| 8 | 只写不读检测 | 给每个桩加**守门校验**（写入后替身自己校验），否则优化器可能删掉整个桩 |
| 9 | `volatile` 必须 | 桩变量必须是 `volatile`，否则 `-O2` 下写入被消除，出现"工具说成功但值没变" |
| 10 | AOB 锚点预筛 | 桩的字节串应含**足够长的固定段**做锚点，防止假命中 |
| 11 | 全量固定字节校验 | 锚点命中后**逐字节**校验固定位，通配位才跳过 |
| 12 | 读取窗口钳制 | 扫描的读窗口必须钳制在 size 内 + 逐页容错；否则越界 → `ERROR_PARTIAL_COPY(299)` → 整块 `return false` → 零命中**且无日志** |
| 13 | 三趟建图 | ①登记所有桩地址 ②按需布指针链 ③回填指针；**顺序颠倒会读到未初始化地址** |
| 14 | 超时与退出码 | 验收脚本要有总超时；工具崩了要能区分"崩"与"没接上" |
| 15 | 控制台编码 | Windows 控制台输出编码与 Python 默认解码不一致会乱码/抛异常，脚本里显式处理 |
| 16 | 计数脚本终局 | 末尾必须打印 `PASS=n FAIL=n SKIP=n` + **一句话结论**，人工只看这一行 |
| 17 | 干跑启动器 | 加 `--dry-run` 只打印将被验证的项与桩清单，**不启动任何进程**，用于先验参数契约 |
| 18 | 交叉核对模板 | 每项记录三元组：`(工具回读, 替身采样, 期望)`，三者一致才 PASS |

## 四、判据与反模式

| 反模式 | 症状 | 修法 |
|---|---|---|
| 替身缺桩就记 FAIL | FAIL 数随替身能力波动 | 探针先分类，缺桩记 SKIP |
| 用宿主 malloc 假地址 | 跨进程读写根本没走到 | 独立 exe + 真实模块基址 |
| 桩变量非 volatile | `-O2` 下"成功但值没变" | 加 `volatile`，加守门校验 |
| 桩无自检 | 扫描零命中时无法定位是桩错还是扫描器错 | 断言扫描结果 == 桩自身地址 |
| 只信工具回读 | 写了但没真写进去（写到自己缓冲） | 加替身侧 Oracle 采样 |
| 不查 mtime | 反复跑出旧结果，误判"修复无效" | 闸门：产物必须新于源码 |
| 只跑一种构建 | Debug 绿 Release 红 | 双构都进验收 |
| 零命中无日志 | 排查时完全瞎 | 扫描器每条失败路径都要有输出 |
| 一次验证所有项 | 失败项互相掩盖 | 先 `--dry-run` 看清单，再分批 |

### 报告必须能回答的三个问题

1. **哪些通了？** —— PASS 清单（且值经过交叉核对）
2. **哪些没通、为什么？** —— FAIL 清单必须带**具体错误文本**（不是"失败"两字）
3. **哪些没验、为什么？** —— SKIP 清单必须带**分类原因**（无位点 / 未实现 / 非地址类）

## 五、替身 + 真机是**互补两层**，不是替代关系

这是最容易搞错的一点。有人以为"替身跑通 = 不用真机了"，或者
"真机能跑 = 不用造替身了"。两者验证的**根本不是同一件事**：

| 层 | 验证什么 | 前提 | 可重复性 | 能进 CI |
|---|---|---|---|---|
| **替身** | 接线是否正确（读地址→链遍历→写值→回读） | 无（自造环境） | ✅ 每次一致 | ✅ |
| **真机** | 位点是否存在 + 副作用是否符合预期 | 需目标程序 | ⚠️ 依赖环境版本 | ❌ |

### 典型协作流程

```
1. 逆向取证 → 得到模块偏移 / 链层次 / AOB 字节串
2. 造替身   → 验全部「地址类接线」                    ← 高频迭代，秒级反馈
3. 跑验收   → 输出 PASS / FAIL / SKIP（SKIP 必带分类原因）
4. ★ 把 SKIP 清单当作真机验证的 TODO 清单
5. 真机补验 → 专验替身验不了的部分（位点存在性、游戏内表现）
6. 回填文档 → 把真机结论写回项目文档，SKIP 从"待验"转为"已知"
```

**第 4 步是精髓**：SKIP 不是"没干活"，而是**自动生成的真机测试用例清单**。
一个设计良好的验收脚本，其 SKIP 明细应当可以直接当 Checklist 用。

### 真机验证后要做的两件事

1. **回填文档**：把「待真机确认」改写为「真机已验证」+ 具体结论，
   **不要留着悬而未决的措辞** —— 否则下一个人会把已确认的事再验一遍。
2. **校准判据分类**：如果真机证明某些 SKIP 其实是位点存在的（只是替身没桩），
   说明探针分类正确；若真机发现位点确实不存在（版本不符），
   则 `SiteAbsent` 语义得到实证，应写入版本适配说明。

> **实证案例**：某项目替身侧 14 项代码钩子恒定 SKIP（替身无钩子桩）。
> 真机逐项验证 → **14/14 PASS**，arm/disarm 与还原全部正常。
> 结论：SKIP 分类正确 —— 若当初按旧实现记 FAIL，就会报出 14 个**假缺陷**。

### 一个反面选项：给替身补钩子桩

给代码钩子在替身里也布桩，让替身侧能验 arm/disarm。
- **收益**：不必每次开目标程序，能进 CI
- **成本**：替身复杂度大幅上升（要真的执行被 hook 的指令、要能还原）
- **建议**：只对**高频回归项**补桩；一次性验证的项留给真机

## 七、和另外三个 replica skill 的关系

```
replica-recon          逆向取证 —— 结论从哪来（哪些是事实、哪些是推测）
      ↓ 产出：模块偏移、指针链层次、AOB 字节串
replica-memory-engine  内存引擎 —— 怎么读怎么写（扫描 / 链遍历 / 钩子）
      ↓ 产出：可调用的读写接口 + 接线好的 flag
replica-mock-harness   ← 本 skill：没有目标程序时怎么证明上面那层真的通了
replica-ui-fidelity    界面 1:1 —— 像素层复刻与复验
```

本 skill 是**收口**：前三个 skill 干完活后，由它给出可决策的验收结论。
