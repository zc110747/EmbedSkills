# 采集端取证：画面不可用与阈值标定

适用于"端侧 AI 明明接上了却什么都检测不到"和"要把某个判定阈值标定到真实数据"。
先记住一条：**0 检出时，先证明画面可用，再怀疑模型，最后才怀疑被测对象没配合。**

## 1. 设备枚举 ≠ 可用

有些驱动会把**同一台物理设备枚举两次**（多视频接口、或 Control 接口被当成视频接口）。
表现：`--list` 里出现两个同名设备，第二个一开会失败。

```
[error] GStreamer error: ... gst_base_src_start (): /GstPipeline:pipeline0/GstMFVideoSrc:cam: Failed to start
[error] Failed to set pipeline to PLAYING (camera busy / unavailable?)
```

- **判据是能否实际上流**，不是列表里有没有。
- 拿设备的真身去核对：Windows 上最省事的是让另一个枚举器报出硬件 ID
  （`ffmpeg -list_devices true -f dshow -i dummy` 会打印 `@device_pnp_\\?\usb#vid_XXXX&pid_YYYY#...`）。
  两个索引指向**同一个 VID/PID + 同一个实例路径**时，就是一个物理设备。
- 推论：**别规划"两个 agent 各占一个索引"的并行采集**，先确认真的有第二个可开设备。

## 2. 量化画面：锐度比亮度可靠

"画面很差"要能被别人复核，就得给数字。两条命令就够（ffmpeg，无需额外依赖）：

```bash
# 亮度分布
ffmpeg -i frame.png -vf "signalstats,metadata=print:file=-" -f null -      # YMIN/YAVG/YMAX
# 锐度代理：先边缘检测，再取平均亮度。边缘越少 => 越糊/被遮挡
ffmpeg -i frame.png -vf "edgedetect=low=0.05:high=0.15,signalstats,metadata=print:file=-" -f null -
```

实测一次**镜头被遮挡**（对比一张确证可用的参考图）：

| 指标 | 现场 | 参考 | 比值 |
|---|---|---|---|
| YAVG 平均亮度 | 62.4 / 255 | 85.7 | 0.73× |
| YMAX 最大亮度 | 227（角落一团过曝） | 206 | — |
| **边缘能量** | **0.769** | **4.287** | **0.18×** |

**要点：只看平均亮度会误判成"只是有点暗"。** 遮挡/失焦的真实特征是**没有锐利边缘**，
所以边缘能量才会掉到 0.18× 而亮度只掉到 0.73×。

**必须排除"自动曝光还没收敛"**：同一个画面至少用**三条互相独立的路径**各取一帧再下结论
（例如 DirectShow 首帧 / Media Foundation 首帧 / 运行 40 秒后从编码流拉的稳态帧）。
三条一致才说明是物理问题。

## 3. 取证时不要重新打开设备

真机常常只有**一个**物理设备。为了看一眼画面而另开一次采集，会把正在跑的 agent 顶掉
（`Failed to start` → agent 退出），把一次"观察"变成一次"破坏"。

改从**正在推的 RTSP 流**拉帧：

```bash
ffmpeg -rtsp_transport tcp -i rtsp://127.0.0.1:8554/<path> -frames:v 1 -y frame.png
```

好处：①**零设备争用**；②拿到的正是 tee 分支上游、**AI 分支同一路**的画面，
验证力比另开一次采集更强（连编码/协商都已包含在内）。

限制管线跑一会儿就退出时，用源元素的 `num-buffers=N` 让它自己收尾，
**不要依赖 `timeout`**（在 Git Bash 里它常被 `C:\Windows\System32\timeout.exe` 遮蔽，
症状是 `无效语法。默认选项不允许超过 '1' 次。`）：

```bash
gst-launch-1.0 -q -e mfvideosrc device-index=0 num-buffers=1 ! videoconvert ! video/x-raw,format=RGB ! pngenc ! filesink location=frame.png
```

## 4. 用已有上报做阈值标定（不重编、不提交现场图）

如果端侧已经把**可反算的中间量**上报了（例：21 个手部关键点的**像素坐标**、2 位小数），
那么标定一个判定阈值**完全不需要改代码或重新编译** —— 上报精度远高于要标定的量。

流程：

1. 把上报**全量落盘**（mock 接收端加 `--dump`，Python 侧加 `-u` 关闭缓冲，
   否则重定向到文件时看不到实时内容）。
2. 写离线脚本**逐字复刻实现里的公式**：下标表、是否含 z、跳过条件、单位，一个都不能凭印象。
   复刻错了会得到"看起来有道理但和 C++ 不一致"的分布。
3. 用**分位数 + 直方图 + 簇间距**看数据，不要只看均值。
4. 按段切分：要有 `--tail N` / `--msg-from..--msg-to` 这类按时间/序号切片的能力，
   否则分不开"稳态段"与"过渡段"。
5. 定阈值取**两簇之间的谷底/间距中点**，并确认它满足实现的设计不变式
   （例：`if / else if` 写成的双阈值，死区就是 `[低, 高]`，**两者交叉会让死区静默失效**）。

### 标定时必须让被测对象保持不动

**过渡帧天然落在两簇之间的谷底，而且数量占优**，会把阈值往上拉。
实测教训：对"每帧中位数"跑 Otsu 得到 **1.3546**，甚至**越过了高阈值**，因为捕获里
大部分帧是手在入画/出画。修法是①要求保持静止再采；②脚本强制把建议值钳到
`高阈值 - 0.05` 并提示"捕获被过渡帧主导，重采"。

同时用**逐帧聚合**而不是逐样本：先把每帧的多个量聚成一个（如四指取中位数），
再对聚合值定阈值，能显著降噪。

## 5. 证据载体：冻结向量，不要提交现场截图

现场帧常含**操作者面部与办公环境**，提交进仓库是隐私问题。
而坐标向量足以钉死阈值，且比图片夹具**更小、更精确、无隐私风险**：

```cpp
// 逐位冻结实测向量，测试里断言阈值行为
static const float kFist[21][3] = { /* 实测 21 点坐标 */ };
```

配套在注释里写清：**采集条件**（设备/分辨率/帧率/模式）、**逐指标量**（四指 ratio 等）、
**为什么这个阈值能分开**（簇间距）、以及**已知的几何限制**。
图片夹具仅在需要验证"上游模型能不能找到该目标"时才不可替代 —— 那时只截目标区域并记录来源与许可。
