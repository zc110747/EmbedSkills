# 像素取证：离屏探针、整帧抓取与结论复核

LVGL 的渲染失败是静默的，唯一可靠的办法是**看像素**。两条路线：

- **路线 A（离屏探针）**：能把 LVGL 单独编成桌面程序时，注册一个 dummy display，
  把画出来的东西拷进内存，然后**对像素做断言**。不需要 SDL、不需要窗口，CI 友好。
- **路线 B（MCU 整帧搬运）**：MCU 工程没有桌面层，但屏幕就在手边；
  把整帧从设备里**搬出来**，在主机侧当普通 PNG 看。

## 一、路线 A：dummy display 探针骨架

```cpp
#define PROBE_W 800
#define PROBE_H 480

// lv_conf.h 若开了 LV_TICK_CUSTOM，真实实现在桌面后端里（会拖进 SDL）。
// 探针渲染一次不需要时钟，stub 掉即可保持无 SDL。
extern "C" uint32_t lvgl_port_tick_get_ms(void) { return 0; }

static lv_color_t fb[PROBE_W * PROBE_H];

void flushCb(lv_disp_drv_t* drv, const lv_area_t* area, lv_color_t* px) {
    const int32_t w = area->x2 - area->x1 + 1, h = area->y2 - area->y1 + 1;
    for (int32_t r = 0; r < h; ++r)
        for (int32_t c = 0; c < w; ++c) {
            const int32_t dx = area->x1 + c, dy = area->y1 + r;
            if (dx >= 0 && dx < PROBE_W && dy >= 0 && dy < PROBE_H)
                fb[dy * PROBE_W + dx] = px[r * w + c];
        }
    lv_disp_flush_ready(drv);
}

int main() {
    lv_init();
    static lv_color_t buf[PROBE_W * PROBE_H];     // 整屏缓冲：一次 flush，拷起来简单
    static lv_disp_draw_buf_t draw_buf;
    static lv_disp_drv_t disp;
    lv_disp_draw_buf_init(&draw_buf, buf, nullptr, PROBE_W * PROBE_H);
    lv_disp_drv_init(&disp);
    disp.hor_res = PROBE_W; disp.ver_res = PROBE_H;
    disp.flush_cb = flushCb; disp.draw_buf = &draw_buf;
    lv_disp_drv_register(&disp);
    // ... 建控件、lv_obj_invalidate(lv_scr_act()); lv_refr_now(nullptr); 然后分析 fb
}
```

要点：

- **渲染前后要把 fb 填成哨兵色**（如 `0xFF00FF`），才能区分「LVGL 没画」和「画成了背景色」。
- 出 **24bpp BMP 样张**（行倒序、每行 4 字节对齐），比看数字直观得多，也方便贴进 issue。
  用 `lv_color_to32()` 取 RGB，这样不必知道 `lv_color_t` 的内部排布。
- 构建上挂成一个可执行目标 + 测试，和普通单测一起进 `ctest`。
  需要 LVGL 源 + 字体源 + 真正要测的那个 widget 的源文件，**不要**链桌面后端。

## 二、像素断言的正确写法（踩过的坑）

1. ⚠️ **字体是 4bpp 抗锯齿的，不要用纯色字面量匹配字形。**
   实测：一个中文标签几百个非背景像素中，颜色**恰好等于**文字色的只有个位数，
   其余都是「文字色 × 底色」的混合灰。
   按纯色匹配会得出「文字没画出来」的错误结论。
   正确做法：**按谓词判定** —— 例如「中性灰（R=G=B）且亮度严格大于底色、
   不超过文字色」；或统计「与底色不同的像素数」。
2. ⚠️ **先 `lv_color_to32(lv_color_hex(x))` 预量化，再和帧里的值比。**
   直接写字面量在 `LV_COLOR_DEPTH 32` 下没问题，改成 16 位（RGB565）后
   颜色会被量化，**所有字面量同时失配**，测试会莫名其妙全挂。
3. ⚠️ **注意圆角会露出父容器底色。** 若控件背景色和窗口底色相同，
   全帧搜「该颜色」会把整个控件区域都算进去（圆角外的四角就是那个颜色）。
   搜索范围要**限制在已知的带状区域**，或给宿主容器一个不同的底色。
4. **「有没有留白」必须用「渲染两次」来证明。**
   浮动标签画在曲线**上层** —— 它盖住的东西在像素上根本看不见。
   所以「曲线像素变少了」证明不了任何事。正确做法：
   **同一份数据渲染两次**（一次有基准线/标签，一次没有），对比曲线**起点 x 坐标**：
   起点右移的距离就是留白宽度。这是唯一能观测到「为标签让了位」的方法。
5. 采样断言要选**真实数据的极端形态**，不要只测一个好看的例子：
   小跨度（数值几乎不变）、大跨度、跳空、跨度 0。
   跨度 0 会走进「人工撑开轴」的分支，不测就发现不了除零/塌陷。

## 三、路线 B：MCU 整帧搬运（lv_snapshot → 串口十六进制 → PNG）

```c
uint32_t need = lv_snapshot_buf_size_needed(lv_scr_act(), LV_IMG_CF_TRUE_COLOR);
// 整屏 RGB565 可达数百 KB：必须显式从 PSRAM 拿（heap_caps_malloc(need, MALLOC_CAP_SPIRAM)），
// 别指望 LVGL 自己的堆分配得下
lv_color_t *buf = heap_caps_malloc(need, MALLOC_CAP_SPIRAM);
lv_img_dsc_t dsc;
lv_snapshot_take_to_buf(lv_scr_act(), LV_IMG_CF_TRUE_COLOR, &dsc, buf, need);
```

- **`LV_IMG_CF_TRUE_COLOR` 时 `set_px_cb` 为 NULL**（见 `lv_disp_drv_use_generic_set_px_cb`），
  意味着 `buf` 就是**原生 `lv_color_t` 的裸行优先位图**，stride = `dsc.header.w`。可以直接按像素取。
- **编码：调色板索引 + 每像素 1 个十六进制字符。**
  先统计整帧颜色直方图（量化到 RGB444 的 4096 个桶就足够），取出现最多的 N 种颜色
  （工控类界面本来是十几种平涂色，取 15 种通常近乎无损）当调色板；
  行首给 `R<idx>:`，行尾给一个 `chk = chk * 31 + palette_index` 的滚动校验和。
  体积相比 `RRGGBB` **降到约 1/6**。
  - ⚠️ **为什么非压不可**：某些 USB-Serial/JTAG 控制台走**逐字节写 TX FIFO** 的旧路径
    （还带一个数十毫秒的丢字节超时），实测吞吐只有几 KB/s。`RRGGBB` 编码下 `STEP=2`
    单帧几百 KB 要传好几分钟；换调色板后 `STEP=1` 的 1:1 整帧只需约 1/6 带宽。
  - ⚠️ **下标必须查表转字符，绝不能写 `'0' + idx`**：`'0' + 10..14` 得到的是
    `:` `;` `<` `=` `>`。后果极其隐蔽 —— 行长度仍是「正常的」，打印出来毫无异样，
    但主机侧 `[0-9A-Fa-f]+` 匹配不上，**整行被静默丢掉**。症状是「缺了大半的行」，
    而设备其实一行没少，极易误判为串口丢数据。
- ⚠️ **逐行 checksum + 缺行检测 + 缺行填成洋红**，三件一起做。长传输一定会丢；
  没有校验的帧只会「看起来有点花」，分不清是渲染问题还是传输问题。
  另一种真相恰恰是**传输完好、解码器丢行** —— 只靠「图看着差不多」会得出完全反向的结论。
- ⚠️ **先统计，再下结论**：`R` 行的**条数与长度直方图**能一眼分开
  「设备没发」/「串口丢了」/「主机没解析」三种情况。长度直方图精确到字节时说服力最强。
- 降采样：按 `STEP×STEP` **分块求平均**（不是取样）。文字是抗锯齿的，取样会丢笔画。
  ⚠️ 但**判定「字有没有挤到一起」必须用 `STEP=1`**：降采样会把 1 px 的网格线和单元格边界
  一起平均掉，相邻文字看起来连成一串 —— 那是降采样的假象，不是渲染缺陷。
  降采样只适合看布局块面与配色（它能省数倍带宽）。
- 采集脚本要提供**「见到结束标记就停」**的选项，秒数只当兜底：
  否则要么白等好几分钟，要么在长帧上等不够。
- ⚠️ **不要用交互式 `monitor` 工具抓这段**：它会插 ANSI 控制序列、还抢终端。
  用 pyserial 自己开端口裸读，配合烧录工具先做一次**带硬复位的**操作
  （如 `esptool read_mac --after hard_reset`）拿到确定的重启时刻，
  就能保证「开机后 N 秒才吐的遥测」一句不漏。
- ⚠️ **`LV_COLOR_16_SWAP` 关时 `lv_color_t` 是原生 RGB565**；一开始就别去猜 bitfield 排布，
  直接取 `c.ch.red/green/blue` 三个字段输出，解码端只做 `x * 255 / 31` 之类的线性还原。

## 四、探针性价比排序（先跑便宜的）

| 顺序 | 探针 | 做法 | 一次能抓什么 |
|---|---|---|---|
| 1 | **控制台 grep** | `grep "glyph dsc. not found" log` | 子集字库缺字。**先跑这个** |
| 2 | **TEXTFIT** | 遍历 label 比自然尺寸与控件尺寸，打印 `dx/dy` | 溢出 / 裁切，唯一能给出「差几个像素」的探针 |
| 3 | **GLYPH** | 逐个码点统计 ink 覆盖率 + ASCII 点阵图 | 缺字形、压缩标志不匹配、字形画错（见 `font-subset.md`） |
| 4 | **SNAP** | 整帧搬运 | 布局、配色、对齐的最终事实 |

## 五、探针不要留在交付固件里

这些探针要往界面里**灌假数据**才能覆盖所有渲染分支。所以：把它们放在独立源文件、
由 `app_main` 里**一行显式调用**接进来，验证完立刻删掉那一行并移出源文件。
留在工程里的风险是：某天有人打开这个开关，固件就开始显示一组看起来完全正常的
**假测量值** —— 这是嵌入式里最危险的一类遗留调试代码。

如果「灌假值」能力以后还要用，把它做成**构建期可选**（Kconfig / `#if`）并且**默认关闭**；
同时把参考实现留一份在工程外部，不参与编译。

⚠️ **灌值的覆盖面要按「显示状态」设计，不是按「数值范围」。**
一个格子的显示态通常不止「有值 / 无值」两种：可能有 **空白（还没读）/ 失败标记 / 数值** 三种，
判定格还有 **空白 / 失败 / 通过 / 未通过** 四种。它们走的是**不同的渲染分支**，
只灌一组「最大值/最小值」覆盖不到。做法：**一帧一态**（每个状态发一帧 SNAP），
并在同一帧里让不同行各处于不同状态，一屏就能对照。

## 六、取证结论本身也要复核（两条真踩过的坑）

搬回来的帧是**证据**，不是**判决**。下面两条都发生过「证据没错、解读反了」：

### (a) 判配色/底色不要靠眼睛，要采样，且要取众数

一次改分组底色后，直接看 PNG 得出「某行底色更深、某类格子没变色」，
与代码逻辑（默认选中状态）直接矛盾。改成**采样**后结论完全相反 —— 是视觉判断错了。

采样有两个必需细节：

- **采样点必须落在文字带之外。** 行高远大于文字高度且文字垂直居中时，
  格子中心上下相当一段范围全是文字。多数采样点打在文字或抗锯齿边缘上，
  会得到「两行同色」这种**假结论**。取格子顶部/底部的窄条。
- **对每个格子取众数色（modal），不要取单点。** 单点采样只要落在抗锯齿像素上就废了；
  众数在平涂界面上几乎是 100% 纯净。

```python
# 逐列/逐格采样，落到文字带外，取众数
c = Counter(v for y in range(ya, yb) for v in rows[y][xa:xb])
r, g, b = frame.pal[c.most_common(1)[0][0]]
```

顺带：**「两行同色」也可能是真的** —— 调色板是「取出现最多的颜色」，
若某个候选色（如选中态的深一档）占比进不了前 N，就会被**量化合并到邻近色**。
所以拿 SNAP 判「两种细微色差是否真的不同」本身就不够用；
这种情况要**直接读 `lv_obj_get_style_bg_color()` 的返回值**，
或在探针里把颜色值一并打印出来。

### (b) 长 dump 里「中间缺行」多数是主机侧丢字节，不是解码器 bug

兆字节级的帧搬运里出现过「一帧缺百余行、且首尾行都在」（缺的是**中间**）。
根因：控制台丢字节时**连带把换行也丢了**，两行粘成一行，行首的 `R<idx>:` 只剩一个，
第二行的行号就「消失」了 —— 校验和不会报错（第一行仍然自洽），只有**行数**对不上。

一眼定位的办法：数每行里 `R\d{3}:` 出现的次数。

```python
multi = [l for l in block if len(re.findall(r'R\d{3}:', l)) > 1]
# multi 非空 ⇒ 主机/控制台丢字节导致行合并，设备其实老实发全了
```

⚠️ **不要一看缺行就往「串口丢数据」/「解码器有 bug」上跳。**
先用 `R` 行的**条数 + 长度直方图 + 多重标签计数**三个统计量把责任方分开，
再决定改哪一端。（同类症状的另一种真相恰好相反：设备一行没少，是解码器的字符表写错
—— 见第三节的 `'0' + idx` 坑。）

## 七、取证脚本清单（可移植到新工程）

| 脚本职责 | 用途 | 依赖 |
|---|---|---|
| 串口采集 | 先用烧录工具造一个确定的重启点，然后 pyserial 裸读存盘；支持「见到结束标记就停」，秒数只作兜底；非交互、byte-exact | pyserial |
| 帧解码 | 解 TEXTFIT / GLYPH / SNAP 三个块：报溢出与缺字、逐行验 checksum、**报缺行数**、解调色板还原 PNG（纯标准库手写 PNG 即可，不需要 Pillow） | 无 |
| 字库生成 | 扫源码字符串字面量 → 调 `lv_font_conv` 重新生成字库（参数用纯 ASCII，规避 Git Bash 的 argv 编码问题） | node + `lv_font_conv` |
| 覆盖校验 | 解析生成字库 `.c` 的 cmap，断言源码用到的字全部在位。**注意 SPARSE cmap 的 `unicode_list` 是相对 `range_start` 的偏移** | 无 |
| 字符集扫描 | 上面两个脚本**共用**：**先剥掉 C 注释**再取字符串字面量 | 无 |
| 设备端探针 | TEXTFIT / GLYPH / SNAP 调色板编码 + 灌值造出全部显示状态（成功 / 失败 / 未读 / 重置后）。**不要编进交付固件** | LVGL `LV_USE_SNAPSHOT` |

典型调用序：

```bash
python serial_capture.py <port> dump.log <seconds> --until "<END marker>"
grep -c "glyph dsc. not found" dump.log        # 必须 0
python gen_font.py                             # 改过界面文案就重跑
python check_font_coverage.py                  # 必须 PASS
python decode_snap.py dump.log frame.png       # 逐帧写 frame_0.png / frame_1.png ...
```
