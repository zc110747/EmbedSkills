# 验证脚本模式与判据

## 一、核心原则

**脚本给出 pass/fail 计数与退出码**，而不是人肉看日志。任何"看日志觉得没问题"的结论都不算验收。

### 1.1 通用计数骨架（串口 / 网络 / 文件产物都适用）

```python
import sys
checks = 0; passed = 0
def chk(name, cond):
    global checks, passed
    checks += 1; passed += 1 if cond else 0
    print(f"[{'PASS' if cond else 'FAIL'}] {name}")
# ... 各项检查 ...
print(f"\n** {passed}/{checks} checks passed **")
sys.exit(0 if passed == checks else 1)
```

- 端口 / 设备等外部输入**从命令行取**（`--port`），不要把本机分配值写死。
- 支持 `--in <文件>` 离线复跑：把一次真实抓取存下来，之后不接硬件也能回归。
- 串口捕获前先 `reset run`，否则错过启动 banner。

### 1.2 已实测有效的几种形态

| 形态 | 做法 | 适用 |
|---|---|---|
| 串口自测 | pyserial 发命令、收响应、逐条 `chk()` 断言（菜单导航 / 按键 / 错误处理等分组） | 有 UART 命令接口的固件 |
| 协议批量验证 | 构造请求报文、解析响应，对每项错误计数（如 `n/n PASS` 或失败项明细） | 网络 / 工业协议 Agent（SNMP 等） |
| **离线逻辑单测** | 纯逻辑（编解码 / 校验 / 报文构造）在 PC 用 gcc 编译成 `.so`/`.dll`，python `ctypes` 调用断言 | 不依赖硬件，CI 友好 |
| 视觉渲染测试 | `PrintWindow` 截图 + Pillow 亮像素检测，验证每页非空白 | 桌面仪表盘 / GUI |
| 网络链路 | `ping` 全尺寸扫、`curl \| grep -q "<特征串>"`、`arp -a` 核 MAC | 以太网 / Web / 推流 |

## 二、★ 验收脚本的"前提"纪律 —— 假 FAIL 先怀疑脚本自己

脚本报 FAIL 时，**先怀疑"前提没成立"，再怀疑产品代码**。最常见的四类自造 FAIL：

1. **动作不产生可观测变化**（目标 == 当前位置 / 已贴着边界）⇒ "等收敛"拿到 `NaN` / 空集。
2. **造前提的常量写死**，没从真值（限位、容量、量程）里挑 ⇒ 撞边界后把"边界现象"误报成"机制缺陷"。
3. **一条断言证多件事** ⇒ 失败无法归因，只能猜；也别把"后来的合理变化"断言成"没收敛"。
4. **断言的机制窗口窄到脚本摸不着**（竞态 / 优先级闸门）⇒ 该由单测构造在途态来证，e2e 只证外部可观测后果。
5. **边界用例写死了数字**，没跟着真值源走 ⇒ 真值源一改，用例就静默变成"另一件事"。
   实测：`("speed 4.1", ...)` 本意是"超上限应被钳位"，量程由 4.0 改到 4.5 之后
   4.1 **反而合法**，用例照样 PASS，但已不再验证"超限钳位"这件事 ——
   属于"绿着失效"。取值方式见 §七.5。

> 与「没报错 ≠ 有数据」同源：**否定性结论一律先查"工具的观测能力"**，别把"我没观测到"直接当成"它没发生"。
> 写任何 e2e 脚本前过一遍这五条。

## 三、「没报错 ≠ 有数据」的正向验证

- 错误日志常被限流，"调用返回 0"不等于"数据正确"。
- 手段：符号取址（`arm-none-eabi-nm <elf> | grep <symbol>`）→ OpenOCD `mdw` / gdb `x/...` 直读内存里的数据结构，比对预期值。
- 例：传感器采样值、双缓冲索引交替、内存池完整性，均靠直读内存而非只看日志。
- 日志开关类特性可由此正向验证：日志宏整体关闭后，UART TX 环形缓冲的写指针必须一个字节都没动过（一次性脚本断言 `head==0 && busy==0` 应全 PASS）。约定：ISR 内不调带互斥量的日志宏。

## 四、性能类判据（先排除"伪性能"）

**方法论**：任何"设备/固件很慢"的结论，先做**双路径对照** —— 绕过外设 vs 经过外设。两者共有的开销一定在主机侧；差异部分才是外设真实开销。

### 4.1 LVGL 首帧 / 首绘卡顿

- 常见根因**不是**字库缓存 miss，而是**一个 screen 第一次被实际绘制时的一次性 CPU 开销**（样式计算 / 排版 / draw-task 构建，可达 ~200 ms，纯 CPU、零 IO）。
- **判据要先排除伪性能**：光看刷新时间变长会误判成缓存未命中。必须同时打印字形缓存的 `miss/hit/evict` 与存储侧读增量；若增量为 0 ⇒ **零 IO**，问题在 CPU，加缓存无用。
- **正解**：抑制 flush 的**离屏预热** —— 把 `flush_cb` 临时换成 dummy（吞帧 + 立即 `flush_ready`），在启动加载页背后把每页渲染一次，把首绘开销提前吃掉。
- **回归脚本**：抓串口 → 解析每次页面切换标记 → 断言首帧 `miss == 0`、零存储读、`|首帧耗时 − 预热均值| ≤ 阈值`，退出码 0/1，并支持 `--in <文件>` 离线复跑。

### 4.2 主机侧读数造成的假延迟（30 ms 级）

```python
data = ser.read(self.ser.in_waiting or 4096)   # ❌ 无数据时会请求 4096 字节
```

读语义是"尽量凑满所请求字节数，凑不满就等超时" ⇒ 每次无数据都空等一整个 timeout，把本该 0.2 ms 返回的字节拖到 ~30 ms。
**正确写法**：`ser.read(self.ser.in_waiting or 1)`。**判据**：软件回环（完全不碰外设）若也有同样的 ~30 ms，则该开销与固件无关。
另：吞吐压测的"平均延迟"受在途窗口与波特率主导，不代表固件固有延迟；真实往返延迟要看无在途窗口的 pacing 模式。

## 五、稳定性与长运行验收

- 压测前后各查一次故障状态寄存器（Cortex-M：CFSR / HFSR）= 0，无总线故障。
- 连续数十次业务请求无失败（验缓冲 / 控制块无泄漏）。
- 长运行浸泡：周期性读取某状态量，确认其 `*_valid` 恒定不冻结（体现"以日志为准"的时序类结论要以最可信的那份日志判定）。
- 外设锁死恢复、初始化顺序这类机制问题按对应外设经验处理。

## 六、双固件（Bootloader + App）端到端验证

Bootloader + App 是**两套独立构建、固定地址共存**，分三层验收：

1. **跳转验证（Golden path）**：直烧 App + 配置 → 复位 → Bootloader 挂载 → 配置 CRC / 向量 / 签名 / 版本全过 → 等待窗口；外设连接则进对应模式（符合设计），未连接则跳 App。
2. **升级验证（升级包路径）**：把升级包 + 校验清单放进可移动介质 → 复位 → Bootloader 检测包 → 擦写 App 区 → 重启 → 打印新 App 版本。再用读回手段确认版本槽 / 配置 CRC。
3. **引擎级验证**：用 GDB 直调编程函数（见 `flash-serial-and-gdb.md`），确认不再挂死、回读一致。

- 任何校验失败都**在擦写前 abort**，已运行的 App 不被破坏（防砖设计）—— 验收时重点确认"**坏包不破坏**"。
- 内存分区与防砖设计细节按工程的链接脚本核对。

## 七、SWD 内存取证的时序与宽容度纪律

### 7.1 同一次 halt 内取完所有区域

连续两次 `dump()` 是**两次独立调试会话**，中间固件**自由运行** ⇒ 两份快照属于不同时刻。

实测：状态结构读到 `TCU1 = 9011`、帧缓冲里却是 `11390`，差 2379 counts。拿这两份数据做"状态 vs 显示是否一致"的断言，得到的是**假 FAIL**（真因是采样时刻不同，不是产品错）。

修法：一次 `init/halt` 内连续 `dump_image` 多个区域。

```python
def dump_multi(cfg, items):
    """items: [(addr, size, outfile), ...] —— 同一次 halt 内全部取完"""
```

### 7.2 运行态：结构严格 + 数值宽容 + 形状校验

运行态下这些字段每帧都在变，逐像素比对必然假 FAIL（本项目 71 字节）：占空比、编码器累计值、实时示数。

**温和但有效的做法**：把这些字段列入白名单，**并为每个字段带一条形状正则** —— 值可以抖，格式必须始终成立。

```python
if st["running"]:
    pm = st["duty_permille"]
    add(1, "{:>2}.{}".format(pm // 10, pm % 10), 0, r"\d{1,3}\.\d", "row1 占空比")
    add(2, "{:>6}".format(st["enc1"]),           5, r"\s*\d{1,6}", "row2 TCU1 累计")
    add(3, _spdr_text(st), UI_SPDR_X // FONT_W, r"SPDR:\s*\d{1,2}\.\d", "row3 SPDR")
```

- **不能整段忽略**：整段跳过就再也发现不了"字段串位 / 格式写坏"。
- **停机态仍走严格逐像素**：没有理由宽容。
- 反向注入自检：把易变字段填成期望字形 ⇒ 应 PASS；硬字段破坏 ⇒ 应 FAIL。

### 7.3 异步命令的收尾必须读回确认

shell / 串口命令由主循环**异步**解析，而主循环一轮里可能含阻塞式刷屏（本项目 OLED 约 250 ms/帧）。"注入完 `stop` 就假定停了" ⇒ 主循环还没解析到，调试会话已 shutdown，**设备带着电机转到下一次验收**。

```python
def stop_and_verify(cfg, elf, tries=3):
    for i in range(1, tries + 1):
        inject(["stop"], cfg, elf, 1200)          # 等足：> 一轮主循环
        arm = _read_u8(cfg, elf, "s_armed")
        if arm == 0:
            return True
        print("[WARN] 第 %d 次 stop 后 s_armed 仍为 %s —— 再试" % (i, arm))
    print("[FAIL] %d 次 stop 后仍未停机！请手动断电。" % tries)
    return False
```

四要点：**等足（> 一轮主循环）→ 读回状态变量 → 重试 → 失败显式告警**。
这属于"比误报更严重"的一类：误报只是白跑一轮，漏报会把硬件留在危险状态。

### 7.4 复用判据，别复制判据

运行态脚本（`verify_ui_running.py`）不重写判据，而是 set `sys.argv` 后**原样调用**停机态脚本的 `main()`：

```python
sys.argv = ["verify_ui_expected.py", "--elf", elf, "--cfg", cfg]
verify_ui_expected.main()
```

两份脚本各写一套判据，改一处忘一处 ⇒ 其中一份静默失效。

### 7.5 用例取值：参数化，不写死

凡涉及**边界、换算、单位**的用例，命令文本与期望值都必须从真值源现算：

```python
def spd_text(v10):                       # x10 → 命令行文本
    return "%d.%d" % (v10 // 10, v10 % 10)

spd_hi_cmd = "speed " + spd_text(spd_max)                     # 上限处（合法）
spd_ov_cmd = "speed " + spd_text(spd_max + spd_step)          # 超上限一步 → 应被钳回
spd_un_cmd = "speed " + spd_text(max(spd_min - spd_step, 0))  # 低于下限一步 → 应被钳回
```

**"特殊点"要用代码搜索，不要挑一个"当时看着对"的值**：

```python
# 找一个真值恰为半整数的合法设定点（定点化硬证据：整数域表达不了它）
probe = None
for v in range(spd_min, spd_max - spd_step + 1):
    if (v * cnt_per) % err_sc == err_sc // 2:
        probe = v
        break
if probe is None:
    sys.exit("[FAIL] 量程内找不到半整数真值点，无法构造定点化硬证据")
```

三个要点：

- **搜索上界写 `spd_max - spd_step`**：紧随其后的"加一步"用例要能合法执行。
- **找不到必须 `sys.exit`** —— 退化成"随便取一个"，这条断言就恒真了。
- 依赖前置状态的用例（"读当前设定值"）要在注释里写明**必须紧邻**，
  中间不得插入任何改状态的用例，否则它悄悄验的是别处的值。

## 八、交付清单（增量汇报模板）

每个模块完成即汇报，用 ✅ 状态收尾：

```
## 交付清单 — <模块名>
- [x] 实现计划已确认
- [x] 编码完成
- [x] Debug/Release 双构零警告（FLASH xx% / RAM xx%）
- [x] 真机烧录验证（Verified OK）
- [x] verify 脚本 <n>/<n> PASS
- [x] 文档已更新
```

**铁律**：任何新模块动手前必须先出实现计划并获确认；每完成一个模块立即增量汇报。
