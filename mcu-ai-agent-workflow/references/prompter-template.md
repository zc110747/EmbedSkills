# 通用提示词（prompter）模板与注意事项

## 为什么需要模板

**不要**直接说"帮我写个 XXX 单片机程序"。要给足 **功能需求 + 硬件信息 + 开发步骤 + 验证手段**，
Agent 才有可执行的步骤。下面的模板来自多个真实工程，逐项目微调即可直接用。

## 模板全文

```
构建 <平台/芯片系列> 的 vscode 项目，实现 <功能描述>。
项目生成后直接构建，仿真，异常时使用 <调试探针> 进行单步调试解决。

## 硬件资源(详细原理图见附件，直接解析补充)
1. <芯片型号>，外部无源晶振 <频率>
2. <已连接的外部器件，如显示屏/存储卡/摄像头，标注哪些可直接调试>
3. 支持调试串口，连接 <TX/RX 引脚>

## 编译环境
1. 使用 cmake + ninja 管理项目
2. 编译工具 <交叉编译工具链>
3. 仿真环境 <openocd + 调试探针>
4. vscode 已经集成 Cortex-Debug，可以实现单步仿真，允许仿真调用
5. python 已经安装，允许直接调用
6. 上述程序已经添加到系统环境中，生成调试文件时不要使用绝对路径

## 工程模块化
1. app: 存放应用逻辑
2. bsp: 存放用户开发的驱动程序
3. Drivers: 厂商 HAL 相关放在这里
4. third_party: 存放第三方库(如 FatFs、lvgl)

## 建议流程
1. 先实现 <最小可运行单元>，测试正常
2. 再逐步集成 <高级功能>
3. 完成后总结项目执行步骤、解决问题，更新到项目下的 README.md 文件中

## 验收标准
1. <可观测的验收现象，如"串口通讯正常""显示屏显示符合预期">

## 附件
原理图.pdf、<已验证的驱动 .c/.h，尽量提供源码而非让 AI 生成>
```

## 段落级要素说明

| 段落 | 作用 | 缺了会怎样 |
|---|---|---|
| 首句"生成后直接构建/仿真/调试" | 授权 Agent 自跑闭环 | Agent 只交代码，不验证 |
| 硬件资源 | 给它真实的引脚/器件/时钟 | 参数靠猜，反复试错 |
| 编译环境 | 声明工具链已就绪且禁绝对路径 | 换机器即失效，或反复问环境 |
| 工程模块化 | 固定分层，避免文件乱堆 | 后续增量改动找不到落点 |
| 建议流程 | 强制分阶段 | 一次性生成大工程，难定位 |
| 验收标准 | 定义"完成"的可观测现象 | 无法判断是否跑通 |
| 附件 | 提供已验证资产 | 外部器件上浪费大量时间 |

## 逐条注意事项

- **对硬件有清晰认知**：功能需求、硬件信息、开发步骤、验证手段都要写进提示词。
- **已验证的驱动源码尽可能提供**：简单内部模块（RTC / GPIO / I2C 等）让 AI 直接写没问题；
  但**外部复杂器件（显示屏、图像传感器、存储卡控制器）让 AI 从零生成参数，常卡一小时以上**。
  提供已调试好的驱动，效率远超让它"猜"。
- **沉淀已验证资产**：把验证过的驱动、第三方库目录打包成可复用包，随工程分发、解压即用。
- **分阶段交付**：先最小单元跑通再扩展。Agent 上限很高（复杂算法链路可长时间连续跑通），
  下限也低（外设参数错、构建漏链接入口，都能卡半小时）。
- **写到提示词里的环境事实要与实际一致**：环境没装好就声明"已就绪"，会让 Agent 陷入
  自我怀疑式的反复试错。
- **提示词存档**：每个工程留一份 `prompter.md`，它就是"给 Agent 的完整上下文"的版本化存档，
  下次同类项目复制微调即可。
