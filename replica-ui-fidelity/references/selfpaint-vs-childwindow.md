# 自绘 vs 真实子窗口：遮挡问题的完整处置

> 这是"代码明明跑了、截图却什么都没有"这类静默故障的头号来源。

## 1. 问题本质

```text
真实子窗口（原生或框架的输入框/按钮）是一个独立的 OS 窗口。
它会：
  ① 用自己的背景色填充自己的矩形（不透明）
  ② 绘制层级上盖在父控件的绘制面之上

⇒ 画在「父控件 OnPaint」里的任何内容，
  只要落在子窗口矩形内，就 100% 被遮住。
```

**症状**：
- 代码路径没报错、逻辑分支确实执行了。
- 全图统计"目标色像素"：**该区域一条都找不到**。
- 人眼去看小像素线（1~2px）时容易误判"好像有"。

## 2. 判定方法（别靠眼睛）

```text
① 对整窗渲染做逐行目标色统计
② 若某区域"预期有 N 条横线"，而统计结果 0 条 ⇒ 被遮挡
③ 反向确认：把该装饰临时改成一个明显的大色块
    （画在父控件上）→ 若大色块也不可见，遮挡成立
```

## 3. 修法：改成同级子控件并置顶

```text
❌ 错误：在父控件 OnPaint 里 DrawLine
✅ 正确：创建一个装饰子控件（如 Panel，背景=强调色）
        · 与其它控件同级（都挂在父控件下）
        · 显示层级置于最顶：BringToFront()
        · 位置/尺寸在布局阶段随行几何同步计算
```

**为什么几何上必然可见**：它与输入框是**兄弟**关系，置顶后绘制顺序在其之上。

```text
_underline = new Panel { BackColor = Accent };
parent.Controls.Add(_underline);
_underline.BringToFront();

// 布局时（随行中心 cy 走）
_underline.Bounds = new Rectangle(
    fieldX + inset,                       // 与字段左右对齐（可内缩）
    cy + underlineOffset,                 // 行中心 + 偏移
    Math.Max(1, fieldW - inset * 2),
    Math.Max(1, thickness));              // 至少 1px，否则 0 高不可见
```

## 4. 常见连带坑

| 坑 | 说明 | 修法 |
|---|---|---|
| 位置用参考值导致空隙 | 参考值对应的是"原件自绘文本的墨迹底边"；本工程文本在真实控件里由系统居中，墨迹底边不同 | 按**自身渲染**重新标定偏移 |
| 厚度为 0 | 缩放后 `round(1.0 * 0.5)` 可能算成 0，或负 inset 算出负宽度 | 一律 `Math.Max(1, ...)` |
| 覆盖到输入框内容 | 装饰控件层级太高、盖住文字 | 让装饰落在文本下方（几何上，不是层级上） |
| 闪烁 | 装饰控件重绘与父控件不同步 | 父控件与装饰都开双缓冲 |
| 布局变化后不同步 | 行几何变了但装饰 bounds 没算 | 把装饰位置放进**同一个** `ApplyLayout` 路径 |

## 5. 同理适用的场景

- 表格单元格的底边线/高亮条。
- 鼠标悬停高亮（不能用父控件绘制）。
- 自定义滚动条滑块的装饰。
- 任何"输入框/按钮附近的装饰线或色块"。

## 6. 复验（必须做）

```text
① 在最终二进制上整窗渲染
② 逐行统计强调色像素，列出 (y, run, x0)
③ 断言：
     - 条数 == 装饰元素数
     - 每条 run ≈ 期望长度
     - x0 落在预期的列区间
     - 相邻 y 差 ≈ 行距
```

**只有这三/四个数都对，才算"可见且位置正确"**。
"我看了一眼好像有"不是判据。

## 7. 反模式

- ❌ 在父控件里画装饰，然后反复微调坐标（怎么调都看不见）。
- ❌ 用"提高父控件刷新率"试图修复遮挡（无效：这是层级问题，不是刷新问题）。
- ❌ 把装饰做成父控件的子控件但忘了 `BringToFront`。
- ❌ 复验只看一次中间版本，不在最终交付二进制上复验。
